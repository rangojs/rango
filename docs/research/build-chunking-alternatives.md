# RSC Client-Asset Chunking: How Rango Compares, and What `clientChunks` Buys It

> Scope note: Rango's confirmed behavior is taken as given — one router ships **one** client chunk containing every route's client components (no per-route split); host sub-apps loaded via dynamic `import()` **do** split per-app; client-chunk granularity tracks RSC server-chunk / dynamic-import-boundary granularity; plugin-rsc's `clientChunks` option exists and was unused by Rango at the time of this report (now shipped as `RangoOptions.clientChunks`). This report situates that behavior against peers and evaluates levers, not re-litigating it.

**The one mechanism underneath all of them:** a dynamic `import()` (or a framework convention that compiles to one) is what tells the bundler to cut a chunk. Next/Remix/TanStack make _route modules_ implicitly dynamic; Vinext makes it _explicit_; Waku/Rango leave routes static and therefore co-resident. This is exactly why Rango ships one chunk per router but splits per sub-app — the sub-app boundary _is_ a dynamic `import()`. That is consistent, not a bug.

> Skeptical flag: the table's CSS columns for Next.js and Remix come from secondary framework docs, and the TanStack Start row has no primary citation in the supplied material. Confidence on the _client-split mechanism_ column is high (it reduces to the dynamic-import boundary fact); confidence on per-framework CSS specifics is medium.

## 2. plugin-rsc `clientChunks` — verified facts

**Verdict: both load-bearing claims `supported`** against `@vitejs/plugin-rsc@0.5.26` source (`dist/plugin-DGxRH4Nv.d.ts`, `dist/plugin-BhzHKRFo.js`).

What the option is:

```ts
clientChunks?: (meta: {
  id: string;            // client reference module id
  normalizedId: string;  // normalized id
  serverChunk: string;   // server chunk holding the client-reference proxy
}) => string | undefined;
```

- **Default behavior (verified):** when the callback is absent, grouping falls back to `meta.serverChunk` (`?? meta.serverChunk` in source). `serverChunk` is `"facade:"+id` for entry chunks or `"shared:"+firstRefId` for shared ones. So **a single server entry statically importing all routes yields exactly one client chunk** — this is the _mechanical root_ of Rango's current per-router granularity, now confirmed at the source level, not just observed empirically.
- **Override behavior (verified):** each distinct returned name becomes a virtual module `virtual:vite-rsc/client-references/group/<name>`, dynamically `import()`-ed per reference. **Distinct names → distinct, independently dynamically-imported client chunks**, regardless of how the server build chunked. The callback can therefore split client components _without_ changing server chunking and _without_ introducing dynamic `import()` at the route source level.
- **CSS rides along (verified):** CSS is collected per `groupChunkId` — split the JS group, get a matching stylesheet. So per-route JS splitting automatically yields per-route CSS at the same granularity, injected via React `data-precedence` links.

Source: [plugin-rsc README](https://github.com/vitejs/vite-plugin-react/tree/main/packages/plugin-rsc), PR adding the option [vite-plugin-react#767](https://github.com/vitejs/vite-plugin-react/pull/767), and the v0.5.26 `dist` type/impl files in-repo.

**Is it the right lever for Rango?** _Conditionally yes — it is the only lever that splits client components without forcing route authors to write dynamic `import()`/`React.lazy` by hand._ It is strictly more surgical than `manualChunks` (which can't see client-reference grouping) and avoids the server-chunk churn that real dynamic-import boundaries cause. But it is **a build-output optimization, not a routing feature** — it does not change _when_ code is fetched unless the resulting chunks are actually lazy on the navigation path. Whether splitting helps depends on real per-route client-component weight, which is unmeasured (see §4).

## 3. What Rango could borrow (ranked)

1. **Route-colocated client modules + a `clientChunks` naming convention (highest leverage, lowest consumer churn).** Map each `"use client"` module under a route directory to a group name derived from the route (e.g. `routes/dashboard/* → cref-dashboard`), exactly as the `per-dir` PoC already does. This gives per-route client+CSS splitting **with zero API change for consumers** — they just organize files by route. This is the borrowed lesson from _all_ of Next/Remix/Vinext (route boundary = chunk boundary) but achieved via plugin-rsc's grouping rather than by making route modules dynamically imported. **Recommended first step.** _Caveat:_ keep React, the router runtime, and `node_modules` on default grouping (the PoC already special-cases `node_modules` and `/src/browser/`) so you split only app client components — splitting shared deps regresses cache reuse.

2. **Keep dynamic `import()` as the _sanctioned_ coarse boundary for sub-apps (already true — formalize it).** Rango's sub-app split is correct and matches Vinext's explicit-import model. Document `import()` of a sub-app as the contract for "I want a separate chunk here," so the per-app split is understood as intentional, not incidental.

3. **Manual `React.lazy` escape hatch for heavy, conditionally-rendered client components (modals, editors, charts).** This is the universal lever (Next `dynamic()`, Vinext `React.lazy`). It needs no plugin work and is the right tool for _intra-route_ heavy components that `clientChunks` grouping would otherwise keep eager. Document it; don't build it.

4. **Adopt a `manualChunks`/min-chunk-size posture only if measurements show fragmentation (lowest priority).** Vinext's `experimentalMinChunkSize≈10 KB` and framework-pinning matter once you have many small route chunks. Per the CLAUDE.md bundle-hygiene rules, Rango already pins React/runtime via `getManualChunks()`. Do **not** chase `experimentalMinChunkSize`: the research note itself says it is **removed in Vite 8 / Rolldown**, and this repo is on `vite@8.0.14` — so that specific knob is a non-starter here. Flagging this as an outdated recommendation in the parallel research.

## 4. Open questions / risks

- **No measured payoff. (biggest risk.)** Splitting only helps if per-route client-component bytes are material and routes are navigated independently. If most client weight is the shared ~115 KB React/RSD baseline + ~50 KB Rango runtime (per CLAUDE.md), per-route splitting of app components may move single-digit KB while **adding HTTP requests and hurting first-load on multi-route initial renders**. _Must benchmark with the bundle-analysis skill before committing._ Until then this is a low-confidence win.
- **`clientChunks` splits build output, not the eager/lazy graph.** A separate group virtual module is dynamically imported, but whether it is _fetched lazily on navigation_ vs. _eagerly because the initial route references it_ depends on the render path. Needs empirical confirmation that grouped chunks are actually deferred for non-initial routes — otherwise it is fragmentation with no latency benefit.
- **CSS ordering non-determinism (GH#1100).** plugin-rsc has a known first-request CSS-order issue between `serverResources` and `clientReferenceDeps` when `cssLinkPrecedence` is on ([vite-plugin-react#1100](https://github.com/vitejs/vite-plugin-react/issues/1100)). More client groups = more `<link>` precedence interactions to validate. Any `clientChunks` adoption needs a dev+prod e2e check for FOUC/cascade order per the project's mandatory dual-mode rule.
- **Shared-component duplication.** A client component imported by two routes: which group wins? With a per-dir/per-route convention a shared component either duplicates into both groups or must be hoisted to a `shared` group. The PoC's naming logic doesn't address de-dup. Needs a defined rule (probably: shared/co-imported refs fall back to default `serverChunk` grouping).
- **`serverChunk` stability across builds.** Default grouping keys off server-chunk identity (`facade:`/`shared:`). If Rango overrides naming, verify group names are deterministic across rebuilds so client chunk hashes stay cache-stable; the PoC derives names from normalized paths, which _should_ be stable, but this is unverified across the real route set.
- **Vinext/TanStack specifics are secondary-sourced.** The `manualChunks` chunk-count ("5–15"), `moduleSideEffects:"no-external"`, and TanStack's per-route claim come from blog/wiki summaries, not source inspection. Treat as directional, not as a spec to match.
- **PoC is explicitly unmerged.** [DONE on this branch] The PoC was productionized into the
  public `RangoOptions.clientChunks` surface (`false` | `true` directory strategy | function),
  not left as an env var.

**Bottom line:** `clientChunks` is verified, real, and the correct _mechanism_ for per-route client splitting in a plugin-rsc consumer — and it's the one peers approximate via dynamic-import boundaries. Rango's current one-chunk-per-router behavior is the _documented default_ of that plugin, not an oversight. The right move is convention-driven grouping (recommendation #1) **gated behind a real bundle measurement** (§4, risk #1) before any consumer-facing commitment.
