A Rango app needs a Vite config with the `rango()` plugin, a `urls.tsx` route tree, and a `router.tsx` that creates the router. On Cloudflare Workers you also write the Worker entry that hands requests to `router.fetch`; on the Node and Vercel presets, `rango()` generates the server entry for you. This page walks through a Cloudflare Workers app. The Node and Vercel differences are at the end.

## Install

Rango requires Node 24 or newer, React 19.2.8 or newer, and Vite 8.

```bash
npm install @rangojs/router react react-dom
npm install -D vite @cloudflare/vite-plugin wrangler
```

## Vite config

```ts
// vite.config.ts
import { cloudflare } from "@cloudflare/vite-plugin";
import { rango } from "@rangojs/router/vite";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [
    rango({ preset: "cloudflare" }),
    cloudflare({
      configPath: "./wrangler.json",
      viteEnvironment: { name: "rsc", childEnvironments: ["ssr"] },
    }),
  ],
});
```

The `rango()` plugin owns the RSC wiring (it bundles `@vitejs/plugin-rsc`), route discovery, and route-type generation. `preset` picks the deployment target: `"node"` (the default), `"cloudflare"`, or `"vercel"`. On Cloudflare, `cloudflare()` comes after `rango()`, and its `viteEnvironment` must name the `rsc` environment with `ssr` as a child.

`@vitejs/plugin-react` is optional. Add `react()` before `rango()` only if you want Fast Refresh or the [React Compiler](/docs/rango/guides/react-compiler).

## The route tree

```tsx
// src/urls.tsx
import { urls } from "@rangojs/router";

import { RootLayout } from "./layouts/root-layout";
import { AboutPage } from "./pages/about";
import { HomePage } from "./pages/home";
import { ProductPage } from "./pages/product";

export const urlpatterns = urls(({ path, layout }) => [
  layout(<RootLayout />, () => [
    path("/", HomePage, { name: "home" }),
    path("/about", AboutPage, { name: "about" }),
    path("/product/:slug", ProductPage, { name: "product" }),
  ]),
]);
```

Handlers are server components: they receive a context and return JSX, and they can be async. Fetch where you render:

```tsx
// src/pages/product.tsx
import { notFound } from "@rangojs/router";
import type { Handler } from "@rangojs/router";

export const ProductPage: Handler<"product"> = async (ctx) => {
  const product = await db.getProduct(ctx.params.slug);
  if (!product) notFound("Product not found");
  return <h1>{product.name}</h1>;
};
```

## The router

Export the router by name. The Node and Vercel presets import the named `router` export, and a default-only export is not picked up.

```tsx
// src/router.tsx
import { createRouter } from "@rangojs/router";

import { Document } from "./document";
import { urlpatterns } from "./urls";

export const router = createRouter({
  document: Document,
  urls: urlpatterns,
});
```

The `Document` is the HTML frame around every page and every error state. It must be a client component, and it should render `<MetaTags />` (the default `charset` and `viewport` tags, per-route `Meta` output, and the theme script) and `<Scripts />`:

```tsx
// src/document.tsx
"use client";

import type { ReactNode } from "react";
import { MetaTags, Scripts } from "@rangojs/router/client";

export function Document({ children }: { children: ReactNode }) {
  return (
    <html lang="en">
      <head>
        <MetaTags />
        <Scripts />
      </head>
      <body>
        <Scripts position="body" />
        {children}
      </body>
    </html>
  );
}
```

`document` is optional. When you omit it, the router uses a default document with exactly this structure. See [createRouter](/docs/rango/reference/create-router) for every router option.

## Serving requests

On Cloudflare Workers, your Worker entry passes the request to the router together with `env` and `ctx`:

```ts
// src/worker.ts
import { router } from "./router";

export default {
  async fetch(request: Request, env: Env, ctx: ExecutionContext) {
    return router.fetch(request, { env, ctx });
  },
};
```

Don't write `export default { fetch: router.fetch }`. Workers call `fetch(request, env, ctx)`, while `router.fetch` takes `(request, { env, ctx })`, so handlers would see an empty `ctx.env` and the `ExecutionContext` would be lost.

Run `npx vite dev` to serve the app from the Workers runtime locally, and `npx vite build` to produce the production Worker. Then `npx wrangler deploy` ships the build output.

## Typed environment

Pass your bindings as the router's type parameter and register them globally, so `ctx.env` is typed in every handler and middleware:

```ts
interface AppBindings {
  DB: D1Database;
  KV: KVNamespace;
}

export const router = createRouter<AppBindings>({
  document: Document,
  urls: urlpatterns,
});

declare global {
  namespace Rango {
    interface Env extends AppBindings {}
  }
}
```

`createLoader()` types `ctx.env` as `any`, so cast or annotate it inside loaders. See [Type Safety](/docs/rango/concepts/typesafety).

## Route types

Named-route typing (`ctx.reverse("product")`, `Handler<"product">`, `href()`) comes from generated `.gen.ts` files. The Vite plugin writes the router-level `src/router.named-routes.gen.ts` itself: before the dev server starts, again when route files change, and during `build`. Run the CLI when you need the files without starting Vite (a fresh clone, a CI typecheck) or want the per-module `*.gen.ts` files that `useReverse()` imports:

```bash
npx rango generate src/
```

Commit the generated files and don't edit them by hand. See the [CLI reference](/docs/rango/reference/cli).

## Node and Vercel

On the `node` and `vercel` presets, `rango()` generates the server entry and imports your named `router` export, so there is no entry file to write and no `cloudflare()` plugin:

```ts
// vite.config.ts
import { rango } from "@rangojs/router/vite";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [rango()], // or rango({ preset: "vercel" })
});
```

The `vercel` preset also needs `@vercel/functions` installed. `vite build` writes a `.vercel/output` directory that you deploy with `vercel deploy --prebuilt` or through Git integration. See [Deploy to Vercel](/docs/rango/guides/deploy-vercel).
