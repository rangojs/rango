Most framework caching pain is one conflation: "is the stored value fresh?" and "should this segment re-render for this client update?" are different questions, and mainstream APIs answer both with one word. Next.js `revalidate = 60` is cache expiry; Remix `shouldRevalidate` is re-render selection; both are called revalidation.

Rango keeps them orthogonal:

| Axis                    | Question                                 | API                                        |
| ----------------------- | ---------------------------------------- | ------------------------------------------ |
| Stored-value freshness  | Is this cached value still good?         | `cache({ ttl, swr, tags })`, `"use cache"` |
| Client-update selection | Should this segment re-render right now? | `revalidate((ctx) => ...)`                 |

They compose: a segment can be cached for ten minutes _and_ re-render instantly after the one action that affects it. You never express one policy by abusing the other.

## Axis 1: cache()

`cache()` wraps a subtree in the tree and stores its rendered segments. On a hit the stored shell streams instantly while any loaders inside re-run fresh — a cached shell with live loader holes:

<CacheHitDemo />

```tsx
// inside urls(({ path, loader, cache }) => [ ... ])
cache({ ttl: 600 }, () => [
  path("/products", ProductsPage, { name: "products" }, () => [
    loader(StockLoader), // never cached: re-runs on every hit
  ]),
]);
```

Handle pushes follow the same split: a handler's pushes are stored and replayed on a hit, while a loader's pushes come from its re-run.

`cache()` needs a store. Configure one on the router, and every `cache()` boundary, cached loader, and `"use cache"` function uses it; without a store, a boundary renders live:

```tsx
import { createRouter } from "@rangojs/router";
import { MemorySegmentCacheStore } from "@rangojs/router/cache";

export const router = createRouter({
  document: Document,
  cache: { store: new MemorySegmentCacheStore({ defaults: { ttl: 60 } }) },
}).routes(urlpatterns);
```

`MemorySegmentCacheStore` suits dev, tests, and single-process servers; `CFCacheStore` (Cloudflare) and `VercelCacheStore` are the distributed stores, all from `@rangojs/router/cache`. `cache({ ttl, swr, tags, key, condition, store })` options are all optional, and omitted `ttl`/`swr` fall back to the store's `defaults`.

This is a Flight segment cache: HTML is still rendered on every request. Caching the rendered HTML shell and resuming only the holes is a separate layer, the `ppr` path option ([PPR](/docs/rango/guides/ppr)). Function-level caching uses the `"use cache"` directive ([use cache](/docs/rango/guides/use-cache)), and a loader's data caches with an explicit opt-in (`loader(Fn, () => [cache({ ttl })])`).

The guards are correctness-first: `cookies()` and `headers()` throw inside cache scopes rather than silently baking one visitor's data into a shared shell. Read request-scoped data in a loader instead. [Freshness](/docs/rango/concepts/freshness) covers keys, SWR, nesting, and every guard.

## Tags and invalidation

Everything cacheable shares one identity scheme and one store. Entries expire by TTL/SWR and are tagged via `cache({ tags })` or runtime `cacheTag(...tags)`. Invalidate by tag:

- `updateTag(...tags)` — awaitable, read-your-own-writes. Use inside an action when the next render must see the new value.
- `revalidateTag(...tags)` — background, non-blocking.

There is no path-based busting; use tags.

## Axis 2: revalidate()

`revalidate()` decides which segments re-run and stream to the client on a navigation or after a server action. Without any `revalidate()`, the defaults are:

| Segment                                                    | After an action | On navigation                        |
| ---------------------------------------------------------- | --------------- | ------------------------------------ |
| The route (`path()`)                                       | re-runs         | re-runs when params or search change |
| Owned by the route (loaders, layouts, parallels inside it) | re-runs         | re-runs when params or search change |
| Loader above the route (on a parent `layout()`)            | re-runs         | kept                                 |
| Layout or parallel above the route                         | kept            | kept, even when params change        |

A segment the client doesn't hold yet always renders. [Execution Model](/docs/rango/concepts/execution-model#partial-revalidation-briefly) explains why the route entry re-runs as a unit.

A predicate returns one of three things. `true` or `false` is a **hard** decision: it ends the chain of revalidators on that segment and overrides the default. `undefined` (or no return) **defers** to the next revalidator or the default. The callback must be synchronous — a returned Promise is ignored — so move async work into a loader.

The predicate receives the action's full context — match _which_ action by reference with `ctx.isAction()` (rename-safe), branch on _what it returned_ with `ctx.actionResult`:

```tsx
import { revalidate } from "@rangojs/router";
import * as CartActions from "./actions/cart";

loader(CartLoader, () => [
  // after an action, re-run only for cart actions; on navigation, keep the default
  revalidate((ctx) => (ctx.isAction() ? ctx.isAction(CartActions) : undefined)),
]),
```

```tsx
import { checkout } from "./actions/checkout";

// on a parent layout (skipped after actions by default): also re-render when
// checkout succeeded; defer to the default otherwise
revalidate((ctx) => (ctx.isAction(checkout) && ctx.actionResult?.ok) || undefined),
```

`ctx.isAction(ref)` matches by reference: one action, several (`ctx.isAction(a, b)`), or a whole module (`import * as CartActions`). Called with no arguments, `ctx.isAction()` answers "was this any action?". It returns `false` on a plain navigation. The same context also carries `actionId`, `formData`, `currentParams`/`nextParams`, `currentUrl`/`nextUrl`, and `defaultShouldRevalidate`.

Pick the idiom by what the default already does. After an action, loaders and the route's own segments re-run by default, and parent layouts are skipped:

- **Add a signal** where the default skips: `ctx.isAction(X) || undefined` on a parent layout re-renders it after `X` and defers otherwise. On a loader or route segment it changes nothing, because they already re-run after every action.
- **Narrow after actions** where the default re-runs: `ctx.isAction() ? ctx.isAction(X) : undefined` re-runs only for `X`'s actions and keeps the navigation default (params or search changed).
- **Avoid bare `ctx.isAction(X)`.** It returns a hard `false` on navigation too, so a loader stops refetching when params change, and when several revalidators share a segment, the first hard `false` means the rest never run.

## Coming from another framework

Same words, different jobs — this is the most common source of misreads:

| You may know                            | Maps to          | Watch out                                                                                                    |
| --------------------------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------ |
| Next.js `export const revalidate = N`   | **Axis 1**       | Same word, opposite meaning. Use `cache({ ttl })` for the Next behavior.                                     |
| Next.js `revalidateTag` / `updateTag`   | **Axis 1**       | Same idea here: tag via `cache({ tags })` / `cacheTag()`, bust via `updateTag()` or `revalidateTag()`.       |
| React Router / Remix `shouldRevalidate` | **Axis 2**       | This is the correct mental model for Rango's `revalidate()`.                                                 |
| HTTP `Cache-Control` / ISR              | Deployment layer | Complete-response deployment layer. A CDN hit bypasses Rango; the store-backed document middleware does not. |
| Remix / React Router `loader`           | live data        | Like Rango loaders — but Rango loaders run in parallel, stream, and can opt into cache.                      |

## Nested caches

The outer cache window bounds the inner: an inner shorter TTL only applies when the enclosing cache recomputes. If a value must be fresher than its surroundings, put it in a loader — that is what the live lane is for. `cache(false, () => [...])` turns caching off for a subtree inside a cached one.
