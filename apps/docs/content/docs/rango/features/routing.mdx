One tree shows every URL, who owns it, what data it loads, what wraps it, and what re-renders after an action — no file-system convention, no hunting across `page.tsx` / `layout.tsx` / `route.ts` siblings. The picture and the code map one-to-one:

```tsx
export const urlpatterns = urls(({ path, layout, loader, loading }) => [
  layout(<ShopLayout />, () => [
    loader(CartLoader),
    path("/shop/:slug", ProductPage, { name: "product" }, () => [
```

## The DSL

`urls()` hands its callback every primitive:

```ts
urls(
  ({
    path, // define a route
    layout, // wrap routes in a layout
    parallel, // parallel routes (slots)
    loader, // attach a data loader
    loading, // opt a segment into skeleton-then-stream
    cache, // cache a rendered subtree
    middleware, // request processing for a subtree
    revalidate, // client-update selection after actions
    intercept, // modal / soft-navigation interception
    errorBoundary, // error boundary for a subtree
    notFoundBoundary, // not-found boundary for a subtree
    transition, // view transitions
  }) => [
    // route definitions
  ],
);
```

## Structure versus config

The tree has one design rule, and everything else follows from it:

- `path()` and `include()` are **structure** — they define URLs and must stay visible in `urls()`. They cannot be hidden in a factory.
- Everything else — `cache`, `loader`, `loading`, `middleware`, `revalidate`, `parallel`, `intercept`, boundaries — is **config**. It attaches to a node via its callback, is importable, and extracts into factories that return arrays (`withAuth()`, `withCaching()`), flattened automatically.

To decide where something can live: **does it define a URL? Structure — stays in `urls()`. Does it modify a node? Config — compose freely.**

```tsx
// A shared config factory — just a function returning helpers
export const withCaching = () => [cache({ ttl: 300 }), loading(<Skeleton />)];

path("/products", ProductsPage, { name: "products" }, () => [withCaching()]);
```

## Composing sub-apps with include()

`include()` mounts a whole `urls()` module under a prefix:

```tsx
// src/urls/shop.tsx
export const shopPatterns = urls(({ path }) => [
  path("/", ShopIndex, { name: "index" }),
  path("/product/:slug", ProductPage, { name: "product" }),
]);

// src/urls.tsx
export const urlpatterns = urls(({ path, include }) => [
  path("/", HomePage, { name: "home" }),
  include("/shop", shopPatterns, { name: "shop" }),
]);
```

`include()` also accepts an async provider to code-split the group into its own chunk, imported on the first request that reaches the prefix instead of at startup:

```tsx
// urls/shop.tsx: `export default shopPatterns`
include("/shop", () => import("./urls/shop"), { name: "shop" }),
```

Build-time discovery still awaits the provider, so route types, `href()`, and prerendering see every route in the split group — lazily loaded, still fully typed.

## Client URL routes

`clientUrls()` is a narrow opt-in for routes whose path and layout values are named client components. Put the definition in a `"use client"` module, default-export it, and mount it directly at the router root:

```tsx
// catalog.client-urls.tsx
"use client";

export default clientUrls(({ path, layout, loader, loading }) => [
  layout(CatalogLayout, () => [
    path("/catalog", CatalogIndex),
    path("/catalog/:productId", ProductPage, () => [
      loader(ProductLoader),
      loading(<ProductLoading />),
    ]),
  ]),
]);

// router.tsx
createRouter().routes(serverUrls).routes(clientUrlPatterns);
```

After hydration, the browser can match a different client route immediately, show its `loading()` UI, and set the wrapping `useOutlet().pending`. The existing partial Flight request is still authoritative: the server matches the route, runs global router middleware and `createLoader()` definitions by ID, and commits content, URL, and history. Hard requests still SSR and hydrate normally.

The supported helpers are `path`, `layout`, `loader`, and `loading`; projected path options are limited to `name`, `search`, and `trailingSlash`. One client definition is allowed per router, with no `include()` or prefix mount. Route middleware/revalidation, parallel routes, intercepts, cache, transitions, boundaries, and PPR are not supported in `clientUrls()`. See the [complete client URL guide](https://github.com/ivogt/vite-rsc/blob/main/packages/rangojs-router/docs/client-urls.md).

## Not-found handling

Two distinct 404s:

1. **No route matches the URL** — the router renders the `notFound` component from `createRouter()`. Automatic.
2. **The route matched but the data doesn't exist** — the handler calls `notFound()`:

```tsx
import { notFound } from "@rangojs/router";

path("/product/:slug", async (ctx) => {
  const product = await db.getProduct(ctx.params.slug);
  if (!product) notFound("Product not found");
  return <ProductPage product={product} />;
});
```

`notFound()` falls back through `notFoundBoundary()` in the tree, then `defaultNotFoundBoundary` from config, then `notFound`, then a built-in. All cases set HTTP 404.

## Dev and production agree

Dev and production resolve every request through the same route trie, built by the same builder. A route cannot match in dev and 404 in production — a parity test stands guard.
