One tree shows every URL, who owns it, what data it loads, what wraps it, and what re-renders after an action — no file-system convention, no hunting across `page.tsx` / `layout.tsx` / `route.ts` siblings. The picture and the code map one-to-one:

```tsx
import { urls } from "@rangojs/router";

export const urlpatterns = urls(({ path, layout, loader, loading }) => [
  layout(<ShopLayout />, () => [
    loader(CartLoader),
    path("/shop/:slug", ProductPage, { name: "product" }, () => [
      loader(StockLoader),
      loading(<ProductSkeleton />),
    ]),
  ]),
]);
```

## The DSL

`urls()` hands its callback every primitive:

```ts
urls(
  ({
    path, // define a route (plus path.json(), path.text(), … response routes)
    include, // mount another urls() module under a prefix
    layout, // wrap routes in a layout
    parallel, // parallel routes (slots)
    loader, // attach a data loader
    loading, // opt a segment into skeleton-then-stream
    cache, // cache a rendered subtree
    middleware, // request processing for a subtree
    revalidate, // which segments re-run on navigations and actions
    intercept, // modal / soft-navigation interception
    errorBoundary, // error boundary for a subtree
    notFoundBoundary, // not-found boundary for a subtree
    transition, // hold content across navigations; view transitions
  }) => [
    // route definitions
  ],
);
```

## Structure versus config

The tree has one design rule, and everything else follows from it:

- `path()` and `include()` are **structure** — they define URLs and must stay visible in `urls()`. They exist only on the `urls()` callback parameter, so they cannot be hidden in a factory.
- Everything else — `layout`, `cache`, `loader`, `loading`, `middleware`, `revalidate`, `parallel`, `intercept`, `transition`, boundaries — is **config**. It attaches to a node via its callback, is importable from `@rangojs/router`, and extracts into factories that return arrays (`withAuth()`, `withCaching()`), flattened automatically.

To decide where something can live: **does it define a URL? Structure — stays in `urls()`. Does it modify a node? Config — compose freely.**

```tsx
import { cache, loading } from "@rangojs/router";

// A shared config factory — just a function returning helpers
export const withCaching = () => [cache({ ttl: 300 }), loading(<Skeleton />)];

// in a urls() tree
path("/products", ProductsPage, { name: "products" }, () => [withCaching()]);
```

[Structure vs Config](/docs/rango/concepts/structure-vs-config) covers factory rules and typing in depth.

## Composing sub-apps with include()

`include()` mounts a whole `urls()` module under a prefix. Its `name` option namespaces the module's route names (`shop.index`, `shop.product`); `{ name: "" }` flattens them into the parent, and leaving it out keeps them private to the module:

```tsx
// src/urls/shop.tsx
export const shopPatterns = urls(({ path }) => [
  path("/", ShopIndex, { name: "index" }),
  path("/product/:slug", ProductPage, { name: "product" }),
]);

// src/urls.tsx
export const urlpatterns = urls(({ path, include }) => [
  path("/", HomePage, { name: "home" }),
  include("/shop", shopPatterns, { name: "shop" }),
]);
```

`include()` also accepts an async provider to code-split the group into its own chunk, imported on the first request that reaches the prefix instead of at startup:

```tsx
// urls/shop.tsx: `export default shopPatterns`
include("/shop", () => import("./urls/shop"), { name: "shop" }),
```

Build-time discovery still awaits the provider, so route types, `href()`, and prerendering see every route in the split group — lazily loaded, still fully typed.

## Client URL routes

`clientUrls()` is a narrow opt-in for routes whose path and layout values are named client components. Put the definition in a `"use client"` module, default-export it, and mount it with `include()` in the server `urls()` tree:

```tsx
// catalog.client-urls.tsx
"use client";
import { clientUrls } from "@rangojs/router/client";

export default clientUrls(({ path, layout, loader, loading }) => [
  layout(CatalogLayout, () => [
    path("/", CatalogIndex),
    path("/:productId", ProductPage, () => [
      loader(ProductLoader),
      loading(<ProductLoading />),
    ]),
  ]),
]);

// urls.tsx — mount through include() like any route module
import { urls } from "@rangojs/router";
import catalogClientUrls from "./catalog.client-urls";

export const urlpatterns = urls(({ include, layout }) => [
  layout(<CatalogRscLayout />, () => [
    include("/catalog", catalogClientUrls, { name: "catalog" }),
  ]),
]);
```

After hydration, the browser can match a different client route immediately, show its `loading()` UI, and set the wrapping `useOutlet().pending`. The partial Flight request that follows is still authoritative: the server matches the route, runs the middleware around the mount on every navigation, runs the `createLoader()` definitions by ID, and commits content, URL, and history. Hard requests still SSR and hydrate normally.

Inside `clientUrls()` the helpers are `path`, `layout`, `loader`, `loading`, `intercept`, `revalidate` (inside a `loader()` use callback, where it runs in the browser), and `transition` (inside a `path()` use callback). Path options are limited to `name`, `search`, `trailingSlash`, and `ppr`. `include`, `parallel`, `cache`, `middleware`, `errorBoundary`, and `notFoundBoundary` throw — put them at or around the `include()` mount in the server tree, which also supplies the URL/name prefixes and the wrapping RSC layouts. See the [Client URLs guide](/docs/rango/guides/client-urls).

## Not-found handling

Two distinct 404s:

1. **No route matches the URL** — the router renders the `notFound` option from `createRouter()` (or a built-in page when unset) with status 404. Automatic.
2. **The route matched but the data doesn't exist** — the handler calls `notFound()`:

```tsx
import { notFound } from "@rangojs/router";

path("/product/:slug", async (ctx) => {
  const product = await db.getProduct(ctx.params.slug);
  if (!product) notFound("Product not found");
  return <ProductPage product={product} />;
});
```

`notFound()` falls back through the nearest `notFoundBoundary()` in the tree, then `defaultNotFoundBoundary` from `createRouter()`, then the `notFound` option, then a built-in `<h1>Not Found</h1>`. No-match and handler-thrown 404s always set HTTP 404. A loader can call `notFound()` too; on a document load its 404 status is only guaranteed when the loader is registered with `{ ssr: false }` ([reference](/docs/rango/reference/create-router#fallback-chain-for-notfound)).

## Dev and production agree

Dev and production resolve every request through the same route trie, built by the same builder. A route cannot match in dev and 404 in production — a parity test stands guard.
