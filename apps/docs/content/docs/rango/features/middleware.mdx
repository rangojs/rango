Middleware runs before and after route handlers using the onion model: code before `await next()` runs on the way in, code after it runs on the way out with the downstream `Response` available. There are two levels with different execution scopes, and the difference matters most for auth. The rule: global middleware wraps server actions, route middleware does not.

## Global middleware: router.use()

Registered on the router instance. Wraps the **entire request** — including server actions, rendering, and no-JS progressive-enhancement re-renders:

```ts
import { createRouter } from "@rangojs/router";

export const router = createRouter<AppEnv>({ document: Document })
  .use(loggerMiddleware) // all routes
  .use("/admin/*", authMiddleware) // pattern-scoped
  .routes(urlpatterns);
```

Scope patterns use the route pattern syntax (`:param`, `:param?`, a trailing `*`) and are prefixed with the router's `basename` automatically. A pattern matches the request URL, not the action: an action is identified by its ID, and any URL that matches a route can carry it. So a pattern-scoped `.use("/admin/*", …)` guards pages under `/admin`, but it is not an authorization boundary for server actions.

## Route middleware: middleware() in the tree

Registered inside `urls()`. Wraps **rendering only** — it does not wrap server action execution. Actions run before route middleware, so when route middleware executes during post-action revalidation it can observe state the action set (cookies, context variables, headers).

```
Request flow (with action):
  global mw → action executes → route mw → render pass

Request flow (no action):
  global mw → route mw → render pass

Fetchable loader call (useFetchLoader / load()):
  global mw → per-loader middleware → loader   (route mw does not run)
```

**Implication for auth:** route middleware cannot guard server actions. Load identity in global middleware (unscoped `router.use()` wraps every action) and check authorization inside the action body. See [Server Actions](/docs/rango/guides/server-actions#auth-inside-actions).

```tsx
import { urls } from "@rangojs/router";

export const urlpatterns = urls(({ path, layout, middleware }) => [
  layout(<AdminLayout />, () => [
    middleware(authMiddleware), // admin routes only
    path("/admin", AdminDashboard, { name: "admin.index" }),
    path("/admin/users", AdminUsers, { name: "admin.users" }),
  ]),
  path("/", HomePage, { name: "home" }), // public — no auth middleware
]);
```

The wrapping form scopes middleware to a subset of routes without introducing a visible layout. Pass an array to register several in order — `middleware([authMw, loggingMw])`; the variadic form `middleware(a, b)` is not supported:

```tsx
middleware(authMw, () => [
  path("/admin", AdminPage, { name: "admin" }),
  path("/admin/settings", SettingsPage, { name: "settings" }),
]),
```

## Writing middleware

```ts
import type { Middleware } from "@rangojs/router";

export const authMiddleware: Middleware = async (ctx, next) => {
  const token = ctx.request.headers.get("Authorization");
  if (!token) throw new Response("Unauthorized", { status: 401 });

  ctx.set("user", await verifyToken(token));
  await next();
  // code after next() runs on the way back out
};
```

Every middleware must either call `next()` or return (or throw) a `Response`. Returning or throwing a `Response` short-circuits the chain and becomes the HTTP response; headers and cookies already set are merged into it. `ctx.env` carries your platform bindings; `ctx.set()` shares data with everything downstream.

Cookies and request headers are free functions, not `ctx` members: `cookies().get("session")` and `headers().get("accept-language")`, both imported from `@rangojs/router`. To set a response header, call `ctx.header(name, value)`; after `await next()` it writes to the real downstream response:

```ts
import type { Middleware } from "@rangojs/router";

export const securityHeaders: Middleware = async (ctx, next) => {
  await next();
  ctx.header("Strict-Transport-Security", "max-age=63072000");
};
```

## Typed context variables

`createVar<T>()` gives type-safe data sharing between middleware and handlers:

```ts
import { createVar } from "@rangojs/router";
import type { Middleware } from "@rangojs/router";

interface AuthUser {
  id: string;
  email: string;
  role: string;
}
// cache: false — per-user data must never bake into a cache() segment
export const CurrentUser = createVar<AuthUser>({ cache: false });

export const authMiddleware: Middleware = async (ctx, next) => {
  const token = ctx.request.headers.get("Authorization");
  if (!token) throw new Response("Unauthorized", { status: 401 });

  ctx.set(CurrentUser, await verifyToken(token)); // type-checked
  await next();
};

// in a handler
const user = ctx.get(CurrentUser); // AuthUser | undefined
```

Use `createVar` for route-local or feature-scoped data; use the global `Rango.Vars` augmentation for app-wide middleware state. Marking a var `{ cache: false }` makes a direct `ctx.get()` of it inside a `cache()` boundary throw, so one user's data can't be served to another; loaders can still read it because they always run fresh.

## Redirects with flash state

```ts
import { createLocationState, redirect } from "@rangojs/router";
import type { Middleware } from "@rangojs/router";

// shared module: the client component that reads it imports the same definition
export const FlashMessage = createLocationState<{ text: string }>({
  flash: true,
});

export const requireAuth: Middleware = async (ctx, next) => {
  if (!ctx.request.headers.get("Authorization")) {
    return redirect("/login", {
      state: [FlashMessage({ text: "Please log in to continue" })],
    });
  }
  await next();
};
```

The target page reads the flash with `useLocationState(FlashMessage)` from `@rangojs/router/client`; `{ flash: true }` auto-clears it after first render. See [Hooks](/docs/rango/reference/hooks#uselocationstatedefinition).

## Why route middleware is never stale

Route middleware wraps **every** render pass — normal renders, post-action revalidation, and no-JS re-renders — so context it sets is never stale. That makes it the safest place for request-shaped context: auth, session, locale. It does not change partial-revalidation boundaries between segments; for shared segment data, put the same named `revalidate()` contract on producer and consumer segments. [Data Flow](/docs/rango/concepts/data-flow) covers the full ladder, and [Execution Model](/docs/rango/concepts/execution-model) covers the exact ordering.
