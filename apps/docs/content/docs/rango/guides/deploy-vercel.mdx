You need your Rango app on Vercel. With the `vercel` preset, `vite build` produces a ready-to-deploy `.vercel/output` directory (Build Output API v3): one streaming Node Function plus your static client assets.

## The short path

Install the platform package and set the preset:

```bash
npm install @vercel/functions
```

```tsx
// vite.config.ts
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";
import { rango } from "@rangojs/router/vite";

export default defineConfig({
  // react() is optional; keep it ahead of rango() if you use @vitejs/plugin-react
  plugins: [react(), rango({ preset: "vercel" })],
});
```

`@vercel/functions` is required — it backs the generated function launcher (`waitUntil`) and `VercelCacheStore`. The build fails with a clear error if it's missing.

Then build and deploy:

```bash
vite build                # produces .vercel/output
vercel deploy --prebuilt  # or deploy via Git integration
```

Under the hood the preset builds like the `node` preset (Vercel runs Node Functions, not Workers): Rango owns the RSC entry and imports the named `router` export of your `createRouter()` module, so export it as `export const router = createRouter(...)`. The preset also folds `process.env.NODE_ENV` for the SSR/RSC build, bundles every server dependency into the function (there is no `node_modules` at runtime), and assembles `.vercel/output` from `dist/` after `vite build`. The generated routing serves files first — hashed assets get `Cache-Control: public, max-age=31536000, immutable` — and sends everything else to the function.

## What runs where

Only client JavaScript, CSS, and public assets are emitted as Vercel static
assets. HTML, Flight responses, prerender payloads, and PPR shells are served
from the streaming Node Function. `Prerender + ppr` can produce a shell during
the build, but that shell is bundled into the function and still runs through
Rango's global and route middleware before its bytes are committed.

The preset does not emit Vercel Prerender Functions, a response `chain`, or a
CDN-stitched PPR resume function. CDN-first shell delivery would start the
response before Rango middleware could authorize, redirect, set headers, or
call `ctx.dynamic()`.

For a completely public and shared route, HTTP `s-maxage` and
`stale-while-revalidate` can instead cache the completed response at Vercel's
CDN. A CDN hit skips the function and all Rango middleware, and it freezes
loader output and resumed PPR holes with the rest of the response. Use this only
when that complete-response contract is intentional.

## Function configuration

Per-function knobs go under `vercel` and are written into `.vc-config.json`:

```tsx
rango({
  preset: "vercel",
  vercel: {
    runtime: "nodejs24.x", // default
    maxDuration: 30, // seconds, default
    memory: 1024, // MB (platform default when omitted)
    regions: ["fra1"], // pin regions (platform default when omitted)
    functionName: "index", // the <name>.func dir + config.json route (default)
  },
});
```

`runtime` must be a `nodejs*` runtime. The preset emits a Node serverless function, so the build fails on any other value; the Edge runtime is not supported.

## Runtime Cache

`VercelCacheStore` wraps Vercel Runtime Cache for the router's segment, item,
response, and PPR shell cache families. Runtime Cache is reached from inside the
function and is separate from Vercel's CDN/ISR cache. Locally there's no
platform cache (no `process.env.VERCEL`), so fall back to an in-memory store and
dev/preview keep working:

```tsx
import { createRouter } from "@rangojs/router";
import {
  MemorySegmentCacheStore,
  VercelCacheStore,
} from "@rangojs/router/cache";
import { getCache, waitUntil } from "@vercel/functions";

const defaults = { ttl: 60, swr: 300 };
const memoryStore = new MemorySegmentCacheStore({ defaults });

function resolveCache() {
  if (process.env.VERCEL) {
    return {
      store: new VercelCacheStore({
        cache: getCache({ namespace: process.env.VERCEL_DEPLOYMENT_ID }),
        waitUntil,
        defaults,
      }),
    };
  }
  return { store: memoryStore };
}

export const router = createRouter({ cache: resolveCache }).routes(/* ... */);
```

The cache factory receives `(env, ctx)`; on Vercel `env` is `process.env` and `ctx` is `{ waitUntil }`, and off-platform `ctx` is `undefined`.

`VercelCacheStore` indexes entries by tag, so `updateTag()` / `revalidateTag()` work as on the other built-in stores. Unlike `CFCacheStore`, it does not version its keys automatically: the per-deploy `getCache({ namespace: process.env.VERCEL_DEPLOYMENT_ID })` above (or the store's `version` option) is what keeps one deploy from reading another deploy's entries. See [Caching & Revalidation](/docs/rango/features/caching) and [Freshness](/docs/rango/concepts/freshness) for cache semantics.

## Multi-app host routers

A multi-app [host router](/docs/rango/guides/host-router) deploys as a **single function** running `hostRouter.match()` for every request — mirroring the Cloudflare single-worker model. Two requirements:

1. The host module exports the `HostRouter` **instance** (default export, or a named `hostRouter`/`router` export) — not a Cloudflare-style `{ fetch }` object, because Rango owns the entry and calls `match()` for you.
2. Point the plugin at the host entry. A host app contains several `createRouter()` sub-apps, so auto-discovery can't pick one; Rango auto-detects a lone `createHostRouter()` file, but set `hostRouter` to be explicit:

```tsx
rango({ preset: "vercel", hostRouter: "./src/worker.rsc.tsx" });
```

```tsx
// src/worker.rsc.tsx
import { createHostRouter } from "@rangojs/router/host";

export const hostRouter = createHostRouter();
hostRouter.host(["admin.*"]).lazy(() => import("./apps/admin/handler.js"));
hostRouter.host(["."]).lazy(() => import("./apps/site/handler.js"));

export default hostRouter; // the instance
```

`{ env, ctx }` is threaded unchanged from the function to each matched sub-app's handler and its `cache(env, ctx)` factory.

## Tracing

Vercel exposes tracing through OpenTelemetry. `createVercelTracing()` (from `@rangojs/router/vercel`) emits the router's `rango.*` phase spans onto the global OTel tracer that `@vercel/otel`'s `registerOTel()` installs:

```tsx
// instrumentation.ts — install the provider, then export the tracing config so
// importing this module is what runs registerOTel(). A Rango/Vite app does NOT
// auto-load `instrumentation.ts` like Next.js does, so a standalone
// registerOTel() that nothing imports is a silent no-op.
import { registerOTel } from "@vercel/otel";
import { createVercelTracing } from "@rangojs/router/vercel";
registerOTel({ serviceName: "my-app" });
export const tracing = createVercelTracing();

// router.tsx — importing `tracing` runs instrumentation.ts (and registerOTel)
import { createRouter } from "@rangojs/router";
import { tracing } from "./instrumentation.js";
export const router = createRouter({ tracing }).routes(/* ... */);
```

`createVercelTracing(opts?)` takes `{ enabled, spans, tracerName, tracer }` (`tracerName` defaults to `"rango"`; `tracer` overrides the global tracer) and emits the same phases as `createCloudflareTracing`: `rango.request`, `rango.middleware`, `rango.action`, `rango.loader`, `rango.handler`, `rango.render`, `rango.ssr`, `rango.response`, and `rango.background`. Caveats:

- Node-runtime only — Vercel custom spans are unsupported on the Edge runtime.
- `registerOTel()` must run before the first request.
- `@vercel/otel` is what unlocks Vercel Session Tracing and Trace Drains.
- The deploy bundles `@vercel/otel` and its `@opentelemetry/*` peers into the function (no `node_modules` at runtime), so they must be installed.

See [Observability](/docs/rango/guides/observability) for the cross-platform tracing model and the telemetry sink that pairs with it.

## Previewing locally without deploying

`vite preview` does not run the assembled function. To preview it, serve `.vercel/output` with filesystem-then-function routing (static files first, everything else to `functions/<name>.func/index.mjs`). The `examples/vercel-basic` app in the Rango repository ships scripts for this: `scripts/preview.mjs` (run as `pnpm preview:vercel`) serves it in place, and `scripts/smoke.mjs` serves it from a temp directory outside the repo for a faithful deploy test (isolated filesystem, ESM, self-contained bundle).
