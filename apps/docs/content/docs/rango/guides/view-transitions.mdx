You want navigations to animate instead of flashing loading skeletons. `transition()` opts a route — or a whole group of routes — into transition-driven navigation, and you choose how far to take it. This page covers the two layers `transition()` controls, where the animation lands in the rendered tree, direction-aware classes, conditional transitions, how intercepted modals interact with layout transitions, and a situation where a view transition runs and changes nothing.

## The two layers

`transition()` does two independent things:

1. **`startTransition` (the foundation).** The navigation commit is driven through React's `startTransition`. That holds the previous content across a same-route navigation (stale-while-revalidate — no loading-skeleton flash) and is the precondition for any view-transition animation. Works on **all** React versions.
2. **`<ViewTransition>` (the animation).** On React 19.3+ (or an experimental build), Rango also wraps the segment content in React's `<ViewTransition>` so the swap cross-fades or morphs. This is the only part that needs 19.3+; Rango feature-detects it, and on React 19.2 it's a no-op while the `startTransition` driving still applies.

A view transition cannot exist outside a `startTransition` — React never activates `<ViewTransition>` otherwise. So once you reach for `transition()`, the only real choice is:

| What you want                          | Config                                              | Effect                                                                                                        |
| -------------------------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Nothing (default nav)                  | no `transition()`                                   | remount + skeleton on param change                                                                            |
| `startTransition` only                 | `transition({ viewTransition: false })`             | hold content; place your own `<ViewTransition>` where you want it                                             |
| `startTransition` + `<ViewTransition>` | `transition({})` / `transition({ enter, exit, … })` | hold + router cross-fade (React 19.3+ or experimental; on 19.2 it degrades to the `startTransition`-only row) |

`createRouter({ viewTransition: "auto" | false })` sets the app-wide default for the third row; a per-segment `viewTransition` wins.

## A cross-fade between pages

The shortest path — a fade between pages that share a layout:

```tsx
import { urls } from "@rangojs/router";
import { Outlet } from "@rangojs/router/client";

function ShopShell() {
  return (
    <div className="shop">
      <NavBar />
      <main>
        <Outlet /> {/* fade applies HERE */}
      </main>
      <Footer />
    </div>
  );
}

export const urlpatterns = urls(({ layout, path, transition }) => [
  layout(<ShopShell />, () => [
    transition({ default: "page-fade" }),
    path("/", ShopIndex, { name: "index" }),
    path("/about", AboutPage, { name: "about" }),
    path("/contact", ContactPage, { name: "contact" }),
  ]),
]);
```

The config values are React `<ViewTransition>` classes: React applies them as `view-transition-class`, so the CSS targets the view-transition pseudo-elements by class:

```css
::view-transition-old(.page-fade) {
  animation: 200ms ease both fade-out;
}
::view-transition-new(.page-fade) {
  animation: 200ms ease both fade-in;
}
@keyframes fade-out {
  to {
    opacity: 0;
  }
}
@keyframes fade-in {
  from {
    opacity: 0;
  }
}
```

Navigating between `/`, `/about`, and `/contact` cross-fades the `<Outlet />` content with the `page-fade` class. The shell (NavBar, Footer) does not animate, because the wrap sits inside the shell, not around it.

## Where the wrap lands

| Segment type                      | Wrap location                                                                                                                                                                                             |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `layout()`                        | Around the layout's **default outlet content** (what `<Outlet />` renders), recursively pushed past nested layouts. Parallel slots (`<ParallelOutlet />`) are siblings, not subtree members.              |
| `path()` / `route()`              | Around the **route's component itself** (the leaf content).                                                                                                                                               |
| `parallel()` / `intercept()` slot | Accepted by the DSL, but slot-level rendering does not currently apply a `<ViewTransition>` wrapper. For modal-specific morphs, use an element-level React `<ViewTransition>` inside the modal component. |

The layout case is the important one: a layout transition does **not** wrap the layout chrome (header, sidebar, modal slot); it only morphs whatever flows through that layout's `<Outlet />`.

## Direction-aware transitions

`transition()` accepts the props of React's `<ViewTransition>` — `enter`, `exit`, `update`, `share`, `default` (the fallback for any unset phase), and `name`. Each phase prop takes a class string or an object keyed by transition type. Every commit the router runs in a transition carries its [`when` kind](#conditional-transitions-with-when) as a type: `"push"`, `"replace"`, `"pop"`, `"action"` or `"revalidate"`, so `{ push: "page", replace: "page", default: "none" }` animates navigations and keeps server action revalidations still. Under `transition()`, Rango also tags forward navigations as `"navigation"` and back/forward navigations restored from the client cache as `"navigation-back"`; a back/forward that has to refetch from the server is tagged `"navigation"`:

```tsx
layout(<ShopShell />, () => [
  transition({
    default: {
      navigation: "slide-left",
      "navigation-back": "slide-right",
    },
  }),
  path("/", ShopIndex, { name: "index" }),
  path("/about", AboutPage, { name: "about" }),
]);
```

```css
::view-transition-old(.slide-left) {
  animation: 250ms ease both slide-out-to-left;
}
::view-transition-new(.slide-left) {
  animation: 250ms ease both slide-in-from-right;
}
/* .slide-right mirrors it; define the @keyframes as usual */
```

`"action"` is only tagged on partial-update action/refetch paths today; ordinary `useAction` / `useActionState` revalidations are not tagged. Don't rely on an `action`-keyed class firing on every form action.

## Grouping without a layout component

`transition(config, () => [...])` creates a transparent layout that applies the config to its children:

```tsx
urls(({ path, transition }) => [
  transition({ default: "fade" }, () => [
    path("/", HomePage, { name: "home" }),
    path("/about", AboutPage, { name: "about" }),
  ]),
  // Outside the wrapper — no transition applied.
  path("/admin", AdminPage, { name: "admin" }),
]);
```

For a one-off morph that should not propagate to siblings, attach it to the route itself — routes are leaves, so the wrap lands on the component:

```tsx
urls(({ path, transition }) => [
  path("/checkout", CheckoutPage, { name: "checkout" }, () => [
    transition({ default: "fade-in" }),
  ]),
]);
```

## Intercept modals don't fire the layout transition

Combine a layout transition with an [intercepting route](/docs/rango/guides/intercepting-routes) and the modal stays out of the animation — because `<ParallelOutlet />` is a sibling of the wrap, not inside it:

| Action                                   | What fires                                                                                                         |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Navigate between pages within the layout | Layout transition fires; `<Outlet />` content cross-fades                                                          |
| Click a link intercepted into `@modal`   | Modal opens via soft navigation; **no** view transition fires on the underlying page                               |
| Submit a form action inside the modal    | Revalidation commits without firing the layout VT; modal subtree identity is preserved (`useActionState` survives) |
| Close the modal via `router.back()`      | Underlying page is restored; **no** view transition fires                                                          |
| Direct URL load of the intercepted route | Full page renders with no modal; the layout transition applies on subsequent in-layout navs                        |

This holds at any depth: if the layout that owns `@modal` is itself nested inside another transitioned layout, the outer transition is pushed past the inner layout into its default outlet content, so the modal slot ends up outside both.

One placement rule follows: **put `<ParallelOutlet />` in layouts, not routes.** A route-level `transition()` wraps the route component itself, so a slot rendered inside that component stays inside the route's VT subtree and modal opens _will_ trigger it. The narrowing only applies at layout boundaries.

## Placing your own `<ViewTransition>`

Prefer animating specific elements yourself? Set `viewTransition: false` — the router contributes no boundary of its own, but still drives the commit through `startTransition` (so React runs `document.startViewTransition` and your own `<ViewTransition>` elements animate) and still holds same-route content:

```tsx
urls(({ path, transition }) => [
  path("/product/:id", ProductPage, { name: "product" }, () => [
    transition({ viewTransition: false }),
  ]),
]);

// ProductPage renders the boundary itself, exactly where it's wanted
// (ViewTransition is exported by React 19.3+ and experimental builds):
import { ViewTransition } from "react";

function ProductPage() {
  return (
    <ViewTransition name="hero">
      <img src={cover} />
    </ViewTransition>
  );
}
```

On a route with `loading()` and slow loaders, `viewTransition: false` is also what removes the view transition that changes nothing; see [When a view transition changes nothing](#when-a-view-transition-changes-nothing). Flip the default app-wide with `createRouter<AppEnv>({ viewTransition: false })`; re-enable one route with `transition({ viewTransition: "auto" })`. A bare `transition({})` inherits the router default; an explicit per-route value always wins. The flag only toggles the boundary — `startTransition` driving and content-hold are on whenever `transition()` is present.

## Conditional transitions with `when`

`transition({ when })` decides, per navigation, whether the navigation holds. It is a **browser** predicate: it runs once per navigation, at the first commit that presents the destination, and never on the server, on the document load, or on progressive-enhancement paths. Return `false` and the navigation commits urgently: the `loading()` skeleton streams and no view transition runs.

Write it inline in `urls()`. The Vite plugin hoists the literal into a `"use client"` module, and the route carries it to the browser as a client reference:

```ts
// Hold unless the navigation leaves the "b" tab (the navigation source):
transition({ when: ({ from }) => from.params.tab !== "b" });

// Hold only for forward navigations inside /list:
transition({
  when: ({ kind, to }) => kind !== "pop" && to.url.pathname.startsWith("/list"),
});

// Hold only after a specific action revalidated the route:
transition({ when: ({ isAction }) => isAction(addToCart) });
```

For a predicate you share between routes or unit-test, export it from a `"use client"` module and import it into the urls file. Location state a `Link` pushed is on `to.state`, read with `Def.read(location)`:

```tsx
// src/transitions.ts
"use client";
import type { TransitionWhenContext } from "@rangojs/router";
import { Slide } from "./location-states";

export function slideWhen({ to }: TransitionWhenContext): boolean {
  return Slide.read(to)?.animate !== false;
}

// src/urls.tsx
path("/photos/:id", PhotoPage, { name: "photo" }, () => [
  transition({ default: "slide", when: slideWhen }),
]);

// A Link that opts its navigation out:
<Link to="/photos/2" state={[Slide({ animate: false })]}>
  Next
</Link>;
```

A predicate runs where its effect lands: the hold is a browser commit decision, so the predicate runs in the browser, and `get()`, `env` and handler state do not exist there. An inline literal may reference module-level imports only when they are client-safe (they are re-emitted into the hoisted module). A free server binding (a module-level binding that is not an import, or a binding of an enclosing function), a server-only import, `import()`, `import.meta` other than `import.meta.env`, or `this` / `arguments` of the enclosing function is a build error that names it; a server function passed by name, or a non-function, fails dev startup, the build and HMR with the route name and pattern.

The context:

| Field      | Meaning                                                                                                                                                            |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `kind`     | `"push"`, `"replace"`, `"pop"` (back/forward), `"action"`, or `"revalidate"` (`router.refresh()`, cross-tab invalidation, a stale entry's background revalidation) |
| `from`     | The committed location being left: `{ url, params, routeName, state }`                                                                                             |
| `to`       | The destination, same shape. It is `from` for `"action"` and `"revalidate"`                                                                                        |
| `isAction` | The `revalidate()` action matcher; `false` off-action                                                                                                              |
| `action`   | `{ id, formData, result, error }` on action commits, the error-boundary commit included                                                                            |

`to.state` holds what the navigation leaves on the history entry: the pushed state plus server `ctx.setLocationState()` for push and replace, the target entry's stored state for pop, and the current entry's state plus action-set state for an action. Middleware-set location state reaches it on a [PPR](/docs/rango/guides/ppr) replay too, because middleware runs on every shell HIT; a route handler's does not, because a HIT runs no handler. A `clientUrls()` cross-route navigation decides at its optimistic swap, before the server responds, so its `to.state` is the pushed state only. On back/forward after a reload, `from.state` and `from.routeName` are `undefined`.

How decisions combine:

- The navigation holds only when **every** committed segment's `when` returns true, kept or re-sent, so a layout the navigation keeps still gates it. The same function on several segments is called once.
- `false` makes the whole navigation urgent. Every `<ViewTransition>` stays in the tree with its classes set to `"none"`, so a route whose predicate flips between navigations never remounts or loses component state.
- That holds for actions and revalidations too: a gated-off action or revalidation commit is urgent, so a segment it re-renders streams its `loading()`. The router commits an action's result after the response arrives, outside the transition React opens for a form action or `useActionState` call.
- Intercept (modal) commits, including a back/forward that opens or closes a modal, are not decided. While a modal is open, an [intercept selector's](/docs/rango/guides/intercepting-routes) `from` is the page under the modal; `transition({ when })`'s `from` is always the location on screen.
- A predicate that throws counts as `false` and is logged with `console.error`.
- `kind` is also the transition type the commit carries, so a [class map](#direction-aware-transitions) keyed `push` animates the commits `when` sees as `"push"`. A pop restored from the history cache commits inside the popstate event, not as a transition, and keeps `"navigation-back"` without a kind.

To skip the transition for one navigation, pass `transition: false`: `router.push(url, { transition: false })`, `router.replace(url, { transition: false })`, or `<Link transition={false}>`. No predicate is called, and the navigation commits the way a `when` returning `false` does. Back/forward, actions and revalidation have no per-navigation options and are unaffected.

## When a view transition changes nothing

You added `transition()` to a route that has `loading()` and a slow loader, and the content shows about 250 ms later than the data arrived. That is a view transition that React starts for a commit that leaves the skeleton on screen. Nothing changes in the DOM, but the browser still runs its default view-transition animation (250 ms in Chromium), and the real reveal waits for it to end. [#1078](https://github.com/rangojs/rango/issues/1078) has the full measurements.

You hit it with one of two shapes, on a click with nothing prefetched:

- **One loader slower than about 320 ms, on a navigation where the route's client component module is still loading when the navigation first renders.** In a production build that is the first navigation to that module; in dev it is every navigation, because the dev server resolves each response's client references asynchronously.
- **Two or more loaders under one `loading()` whose data lands at different times, the last one later than about 320 ms.** Module state does not matter.

A fully prefetched click commits complete and does not hit it, and neither does a loader that lands before the skeleton has been up for 300 ms.

### Why it happens

The navigation renders, the route's `loading()` boundary suspends, and the skeleton commits. When the first thing the boundary waits on lands (the client module, or the first loader), React retries it. The retry suspends again on the slower loader and commits with the skeleton still in place, throttled to 300 ms after the skeleton committed. That retry is eligible for a view transition and the router's `<ViewTransition>` is on its path, so React calls `document.startViewTransition`. When the slower loader lands, its reveal is the next view-transition commit, and React holds it until the running transition finishes. No router update is involved, and the router does not steer or cancel React's retry. This is React's behaviour as of 19.3.0.

Measured in the router's test app (a 400 ms loader, or loaders of 100 ms and 400 ms; median of 5 fresh pages per cell; Chromium), "starts" is the number of `document.startViewTransition` calls during the click and "content" is when the 400 ms loader's value is on screen, in ms after the click:

| `transition()` on the route | Shape       | Production: starts / content | Dev: starts / content |
| --------------------------- | ----------- | ---------------------------- | --------------------- |
| default                     | one loader  | 3 / 649                      | 3 / 666               |
| default                     | two loaders | 3 / 665                      | 3 / 680               |
| `{ when: () => false }`     | one loader  | 0 / 408                      | 0 / 423               |
| `{ when: () => false }`     | two loaders | 0 / 412                      | 0 / 414               |
| `{ viewTransition: false }` | one loader  | 0 / 408                      | 0 / 417               |
| `{ viewTransition: false }` | two loaders | 0 / 409                      | 0 / 414               |

With the route's client module already loaded, the one-loader shape in production starts 2 view transitions and shows the content at 416 ms; two loaders still start 3 (649 ms), and dev still starts 3 for either shape.

### Getting rid of it

Two options remove it, in dev and in production:

- **`transition({ viewTransition: false })`** places no router `<ViewTransition>` for the segment that declares it, so React has nothing of that segment's to animate on the retry commit. The navigation still commits through `startTransition`, so same-route content is still held. You give up the router's cross-fade there. It only covers the segment it is set on: a layout above the route that declares its own `transition()` still wraps the route in a router `<ViewTransition>`, and the idle transition stays. Set it on every segment in the chain that declares `transition()`, or app-wide with `createRouter({ viewTransition: false })`.
- **`transition({ when })` returning `false`** commits the navigation urgently, with every router `<ViewTransition>` of the navigation rendered with every class `"none"`, and React starts no transition for it. One `when` on one segment is enough, because a `false` gates the whole navigation off. On a same-route navigation the `loading()` skeleton streams instead of the previous content being held, and nothing animates. Use it when `kind`, `from` and `to` tell you which navigations hit the shape.

```tsx
path("/report/:id", ReportPage, { name: "report" }, () => [
  loader(SummaryLoader),
  loader(DetailsLoader),
  loading(<ReportSkeleton />),
  // The loaders land at different times; keep the hold, skip the cross-fade.
  transition({ viewTransition: false }),
]);
```

### A `<ViewTransition>` you placed

A `<ViewTransition>` of your own that stays on screen across the navigation, for example around a layout's `<Outlet />`, takes part in the same commits and starts the same idle transition, whichever router option is set. The router only controls its own boundaries, so this one is yours to configure. Measured with such a boundary around the outlet and a 400 ms loader under `loading()`:

| Route                                            | Production: starts / content | Dev: starts / content |
| ------------------------------------------------ | ---------------------------- | --------------------- |
| no `transition()`                                | 2 / 618                      | 2 / 630               |
| default `transition()`                           | 3 / 646                      | 3 / 665               |
| `transition({ when: () => false })`              | 2 / 630                      | 2 / 631               |
| `transition({ viewTransition: false })`          | 3 / 663                      | 3 / 665               |
| no `transition()`, your boundary `update="none"` | 0 / 407                      | 0 / 410               |

With `update="none"` on that boundary React started no view transition for the click, but the boundary then no longer animates the real navigation's update either (no cross-fade of the outlet). Chromium is the only engine measured.

## Testing a transition() route

On React 19.3+ a transition commit briefly keeps the exiting `<ViewTransition>` host in the DOM next to the entering one (hidden, carrying React's `vt-*` attributes) for a few hundred milliseconds. A strict Playwright locator on a test id that exists in both the old and the new view (same route with different params, or a hard load followed by a revalidation commit) resolves to two elements during that window. Target the entering host, which is appended after the exiting one:

```ts
const featurePage = page.getByTestId("feature-page").last();
await expect(featurePage).toBeVisible();
```

Waiting for `toHaveCount(1)` first is not enough: the count passes through 1 before the second host is inserted.

Unit-test a `when` with `runTransitionWhen(when, { kind, from, to, action })` from `@rangojs/router/testing`; it builds the same context and returns `{ applied, gatedOff, context }`. `renderRoute` decides `router.navigate()` as `kind: "push"` and `router.refresh()` as `kind: "revalidate"`. Pop, action and `clientUrls()` optimistic-swap decisions are e2e territory. See [Testing](/docs/rango/guides/testing).

## Recommendations

- **Don't stack `transition()` on every layout level.** Nested configs both wrap the deepest outlet content, so two VTs fire on every inner nav. Pick the level where the morph belongs and apply it once.
- **Need a modal-only morph?** Per-slot `transition()` is a no-op at render time today — use an element-level React `<ViewTransition>` inside the modal component (or a CSS animation).
- **Action revalidation inside a modal is safe.** Modal subtree identity is preserved across the round-trip, so `useActionState`, focus, and scroll all survive.
- Element-level `<ViewTransition>` (imported directly from React, morphing named elements across pages) composes with Rango's segment-level wraps as usual; Rango doesn't intercept those.
