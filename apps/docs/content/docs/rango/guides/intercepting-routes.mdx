---
title: Intercepting Routes
description: Open a route as a modal or slide-over on soft navigation while the same URL serves the full page on hard navigation.
type: guide
---

You want a product page to open as a modal when the user clicks a link, but load as a full page when the URL is visited directly or shared. `intercept()` does exactly that: during soft (client-side) navigation it renders an alternate component into a slot while keeping the background route; hard navigation gets the full page.

If you want a region that **always** renders alongside the page (sidebar, multi-column layout), that's a permanent [parallel slot](/docs/rango/guides/parallel-routes), not an intercept. Intercepts only swap on soft navigation.

The signature is `intercept(slot, routeName, handler, config?, use?)`:

- `slot` is the `@name` slot the intercept renders into. The layout places it with `<ParallelOutlet name="@modal" />`.
- `routeName` is the target route. A bare name (`"product"`) is the global route name; a dot prefix (`".product"`) resolves inside the current `include()` scope. Declare the intercept in a layout that wraps the target route: the router finds intercepts by walking up the target route's own layout chain.
- `handler` is the component or handler rendered in the slot.
- `config` is an optional `{ when }` object (see [Conditional intercepts](#conditional-intercepts-with-when)). With no config, pass the `use` callback as the 4th argument.

## The shortest path

```tsx
import { urls } from "@rangojs/router";
import { Outlet, ParallelOutlet } from "@rangojs/router/client";

function ShopLayout() {
  return (
    <div className="shop">
      <Outlet />
      <ParallelOutlet name="@modal" />
    </div>
  );
}

export const urlpatterns = urls(
  ({ path, layout, intercept, loader, loading }) => [
    layout(<ShopLayout />, () => [
      intercept(
        "@modal", // Slot name
        "product", // Route name to intercept
        <ProductModal />, // Modal component
        () => [loader(ProductLoader), loading(<ProductModalSkeleton />)],
      ),

      path("/shop", ShopIndex, { name: "index" }),
      path("/shop/product/:slug", ProductPage, { name: "product" }),
    ]),
  ],
);
```

| Navigation type                   | What renders                                         |
| --------------------------------- | ---------------------------------------------------- |
| Click link to `/shop/product/abc` | `<ProductModal />` in `@modal`, background preserved |
| Direct URL `/shop/product/abc`    | Full `<ProductPage />`                               |
| Browser back                      | Modal closes, previous state restored                |

## Modal chrome and closing

Wrap the intercept content in a modal layout inside its use callback. Like any layout, it renders the intercept content through `<Outlet />`, not a `children` prop. Only the first `layout()` in an intercept's `use()` is applied.

```tsx
intercept("@modal", "product", <ProductModalContent />, () => [
  layout(<ModalWrapper />), // Wraps the modal content via <Outlet />
  loader(ProductLoader),
  loading(<ProductModalSkeleton />),
]);
```

Close by navigating: `router.back()` restores the background route.

```tsx
"use client";
import { Outlet, useRouter } from "@rangojs/router/client";

// Used as the intercept's layout: layout(<ModalWrapper />)
export function ModalWrapper() {
  const router = useRouter();

  return (
    <div className="modal-overlay" onClick={() => router.back()}>
      <div className="modal" onClick={(e) => e.stopPropagation()}>
        <button onClick={() => router.back()}>Close</button>
        <Outlet />
      </div>
    </div>
  );
}
```

## Conditional intercepts with `when`

`when` goes in a config object as the 4th argument; the use items then move to the 5th argument. It is a synchronous match-time selector that receives `from` and `to` (URLs), `fromRouteName` and `toRouteName` (named routes only), `params` (the target's), `segments` (the client's current segment path and ids), `request`, and `env`. Omit it and the intercept always activates. The config type is not exported; pass an object literal.

```tsx
intercept(
  "@modal",
  "product",
  <ProductModal />,
  // Only intercept when coming from a different section
  { when: ({ from }) => !from.pathname.startsWith("/shop/product/") },
  () => [loader(ProductLoader)],
);

// Only intercept when opened from the shop index
intercept("@modal", "product", <ProductModal />, {
  when: ({ fromRouteName }) => fromRouteName === "index",
});
```

Pass an array of predicates for AND logic; all must return true:

```tsx
intercept(
  "@modal",
  "product",
  <ProductModal />,
  {
    when: [
      ({ from }) => from.pathname.startsWith("/shop"),
      ({ params }) => params.slug !== "featured",
    ],
  },
  () => [loader(ProductLoader)],
);
```

`when` is not re-evaluated during action revalidation, so an open modal stays open after an action.

## Middleware and data

Intercepts support their own middleware chain. For an intercept request the full order is:

```
global mw (router.use) -> route mw (urls middleware()) -> intercept mw -> intercept loaders + handler
```

The intercept's loaders start before its handler is called, so they run in parallel with it. If intercept middleware returns a `Response` (a redirect, for example), the intercept stops there.

```tsx
intercept("@modal", "product", <ProductModal />, () => [
  middleware(async (ctx, next) => {
    // Runs only for this intercept, after global and route middleware
    ctx.set("interceptSource", "modal");
    await next();
  }),
  loader(ProductLoader),
]);
```

The intercept handler reads context variables set by all upstream middleware layers (global, route, intercept-specific). You can register multiple loaders, each with its own config:

```tsx
intercept("@modal", "product", <ProductModal />, () => [
  loader(ProductLoader, () => [cache()]),
  loader(ProductCartLoader, () => [revalidate(() => true)]),
  loader(RecommendationsLoader),
]);
```

See [Middleware](/docs/rango/features/middleware) and [Loaders](/docs/rango/features/loaders).

### Revalidating an intercept

An intercept has no segment-level `revalidate()`. Its handler and layout re-render every time the intercept resolves live: each intercepted navigation, and each action submitted while the modal is open. When the segment cache or a prerendered intercept variant serves the modal, the stored handler output is reused and only the loaders run. Each loader decides for itself through its own `revalidate()`, with the normal loader defaults.

A `revalidate()` placed directly in the intercept's `use()` (or returned from its handler's `.use`) throws at definition time. Attach it to the loader:

```tsx
// Throws: revalidate() is not valid inside intercept("@modal", "product") use()
intercept("@modal", "product", <ProductModal />, () => [
  revalidate(() => false),
  loader(ProductLoader),
]);

// Correct: the loader owns the decision
intercept("@modal", "product", <ProductModal />, () => [
  loader(ProductLoader, () => [revalidate(() => false)]),
]);
```

### Revalidation across entries

Handler and layout `ctx.set()` data follows the same rule as elsewhere: intercepts see data produced in the current render pass, but a partial action revalidation only recomputes segments that actually revalidate. If the intercept depends on data established by an outer layout or handler, the producer is the side that needs a contract, because outer layouts are skipped during partial action revalidation unless they opt in. The intercept side needs none by default: its handler re-renders on every action while the modal is open, and its loaders re-run after every action. If you narrow an intercept loader with its own `revalidate()`, compose the producer's contract into it so the two stay in step:

```tsx
import type { Revalidate } from "@rangojs/router";
import * as ProductActions from "./actions/product";

export const revalidateProductShell: Revalidate = (ctx) =>
  ctx.isAction(ProductActions) || undefined;

layout(ProductLayout, () => [
  revalidate(revalidateProductShell), // producer reruns
  intercept("@modal", "product", <ProductModal />, () => [
    loader(ProductLoader, () => [
      revalidate(revalidateProductShell), // reruns with the producer
      revalidate(() => false), // otherwise keep the loaded data
    ]),
  ]),
]);
```

Compose multiple contracts if the intercept depends on multiple upstream domains. Refreshing the intercept never implicitly rebuilds non-revalidated outer segments.

## What an intercept's use() accepts

An intercept's `use()` (and its handler's `.use`) accepts:

- `loader()`, with its own `revalidate()` and `cache()` inside it
- `middleware()`
- `loading()`
- `layout(Chrome)`: the modal chrome, without `use()` items of its own
- `transition()`

Everything else throws at definition time with a pointer to where it goes:
`revalidate()` onto the loader, `errorBoundary()` / `notFoundBoundary()` onto
the enclosing layout (see [Errors in an intercept](#errors-in-an-intercept)), and `cache()` onto the target route.

### Caching an intercept

To cache a modal, put `cache()` on the target route (or a layout above it).
An intercept navigation is cached under that scope with its own `intercept:`
key, so it never collides with the full-page render of the same URL. For
finer control, use `"use cache"` in the intercept handler, or cache the
intercept's loader: `loader(ProductLoader, () => [cache()])`.

## Errors in an intercept

An intercept has no boundary of its own. When the intercept's handler or one
of its loaders throws, or calls `notFound()`, the modal slot renders the
`errorBoundary()` / `notFoundBoundary()` of the layout or path that declares the
intercept, or the nearest ancestor that has one. The intercepted route's own
boundaries are not consulted: the modal renders in the declaring layout's slot,
not in the route. On a handler error the modal layout and the background page
stay mounted, and the status is 500 / 404. A thrown `Response` (`redirect()`)
still short-circuits the navigation.

With `loading()`, an async handler streams after the response has started, so
its rejection is not caught on the server. Wrap the modal layout's `<Outlet />`
in a client error boundary.

An `errorBoundary()` or `notFoundBoundary()` placed directly in the intercept's
`use()` (or returned from its handler's `.use`) throws at definition time. Put
it on the enclosing layout:

```tsx
// Throws: errorBoundary() is not valid inside intercept("@modal", "product") use()
intercept("@modal", "product", <ProductModal />, () => [
  loader(ProductLoader),
  errorBoundary(<ModalError />),
]);

// Correct: the declaring layout's boundaries handle the intercept's handler and loaders
layout(<ShopLayout />, () => [
  errorBoundary(<ShopError />),
  notFoundBoundary(<ProductNotFound />),
  intercept("@modal", "product", <ProductModal />, () => [
    loader(ProductLoader),
  ]),
]);
```

## Self-contained modals with handler.use

An intercept handler can carry its own middleware, loaders, loading state, and modal layout via `.use`, so the modal travels with its own data and chrome:

```tsx
import { layout, loader, loading, type Handler } from "@rangojs/router";

const QuickViewModal: Handler = async (ctx) => {
  const product = await ctx.use(ProductLoader);
  return <QuickView product={product} />;
};
QuickViewModal.use = () => [
  loader(ProductLoader),
  loading(<QuickViewSkeleton />),
  layout(<ModalChrome />), // ModalChrome renders <Outlet />
];

intercept("@modal", "product", QuickViewModal);
```

Conditional activation stays config-only: `when` goes on the mount-site `intercept()` call, never inside `.use`. Boundaries go on the enclosing layout (see [Errors in an intercept](#errors-in-an-intercept)). Explicit `use()` at the mount site merges after the handler's defaults; see [handler.use](/docs/rango/guides/handler-use).

## Interaction with view transitions

Opening a modal does **not** fire the owning layout's `transition()`. Rango narrows the layout's `<ViewTransition>` wrap to the layout's default outlet content, so the `<ParallelOutlet />` where the modal mounts is a sibling of the wrap, not inside it. Form actions submitted from inside an open modal commit without firing the underlying layout's transition, the modal subtree survives revalidation without remounting (so `useActionState` survives), and closing the modal restores the page without a stray transition.

Two caveats:

- For a modal-only morph (intercepted URLs changing while the modal stays open), use an element-level React `<ViewTransition>` inside the modal component. A `transition()` on `intercept()` is accepted by the DSL but not applied to slot rendering.
- Route-level `transition()` wraps the route component itself, so a `<ParallelOutlet />` rendered directly inside that route component would sit inside the route's transition subtree. Mount the slot in a layout instead when combining intercept modals with route-level transitions.

See [View Transitions](/docs/rango/guides/view-transitions).

## Interaction with prerender

When the intercept's target route uses `Prerender`, the intercept handler is also resolved at build time and stored alongside the main pre-rendered segments. Intercept navigations to pre-rendered routes are then served from the prerender store without running handler code at runtime.

- **Build time:** the intercept handler is resolved with `BuildContext` and stored as an intercept variant of the route's entry. `when` conditions are skipped, so every intercept is pre-rendered unconditionally.
- **Runtime:** an intercept navigation serves the intercept variant (frozen handler, fresh loaders); a direct navigation serves the main variant. `when` is still evaluated at runtime. If no intercept prerender entry exists, resolution falls through to the live intercept path.

Loaders inside the intercept always run fresh at request time, as on any pre-rendered route. See [Prerender](/docs/rango/guides/prerender).
