You need a layout with more than one region that loads and revalidates on its own schedule: a sidebar next to the main panel, a cart preview, a notifications rail. `parallel()` declares named slots that render alongside the page; each slot can carry its own loader, skeleton, and revalidation rule. The owning layout (or route) places each slot with `<ParallelOutlet name="@slot" />`.

One boundary first: parallel slots **always** render alongside the page. If you want a modal that appears only on soft navigation and shows the full page on hard navigation, that's [Intercepting Routes](/docs/rango/guides/intercepting-routes), not this guide.

Slot rules:

- Slot names start with `@` and must not contain `.` (a dot is rejected when the slot is defined).
- A slot value is a handler function, a React element, a `Static()` definition, or a slot descriptor `{ handler, use }` (see [Scoping explicit use()](#scoping-explicit-use-broadcast-vs-slot-local)).
- `parallel()` can't be nested inside another `parallel()`, and neither `layout()` nor `intercept()` can be declared inside one.

## Declare slots, render them with ParallelOutlet

```tsx
import { urls } from "@rangojs/router";
import { Outlet, ParallelOutlet } from "@rangojs/router/client";

function DashboardLayout() {
  return (
    <div className="dashboard">
      <aside>
        <ParallelOutlet name="@sidebar" />
      </aside>
      <main>
        <Outlet />
      </main>
      <div className="notifications">
        <ParallelOutlet name="@notifications" />
      </div>
    </div>
  );
}

export const urlpatterns = urls(({ path, layout, parallel }) => [
  layout(<DashboardLayout />, () => [
    parallel({
      "@sidebar": () => <Sidebar />,
      "@notifications": () => <NotificationPanel />,
    }),

    path("/dashboard", DashboardIndex, { name: "dashboard.index" }),
    path("/dashboard/analytics", Analytics, { name: "dashboard.analytics" }),
  ]),
]);
```

`<Outlet name="@sidebar" />` is equivalent to `<ParallelOutlet name="@sidebar" />`. The convention is a bare `<Outlet />` for the default content and `<ParallelOutlet />` for named slots.

Slot handlers receive the same context as route handlers: `ctx.params`, `ctx.use()` for loaders and handles, and `ctx.get()`:

```tsx
parallel({
  "@sidebar": (ctx) => <Sidebar userId={ctx.params.userId} />,
  "@related": (ctx) => {
    const user = ctx.get("user");
    return user ? <UserSidebar user={user} /> : <GuestSidebar />;
  },
});
```

The parent handler always runs before its parallels (handler-first), so its `ctx.set()` values are visible. Visibility follows tree structure: layout-level parallels see layout data but not path handler data (the path is a separate entry); parallels inside a `path()` or its orphan layouts see both. That holds for full renders. During a partial action revalidation only the revalidated segments re-run; see [Revalidation](#revalidation).

## Streaming: loading() decides who waits

Parallels with `loading()` are independent streaming units. They don't block the parent layout or sibling routes during SSR:

```tsx
// Sidebar streams independently: the page renders immediately
parallel({ "@sidebar": () => <Sidebar /> }, () => [
  loader(SlowSidebarLoader),
  loading(<SidebarSkeleton />),
]);

// Cart data blocks the layout: it must be ready before paint
parallel(
  { "@cartBadge": () => <CartBadge /> },
  () => [loader(CartCountLoader)], // No loading() = awaited
);
```

| Configuration       | Behavior                                                                                            |
| ------------------- | --------------------------------------------------------------------------------------------------- |
| With `loading()`    | Skeleton renders immediately; the loader streams data when ready; the rest of the page doesn't wait |
| Without `loading()` | The slot's loaders block the parent layout. Use it for critical above-the-fold data                 |
| Soft navigation     | Loaders resolve in the background; the existing slot UI stays visible, with no skeleton flash       |

## A @meta slot for per-route metadata

Slot handlers can push handle data with `ctx.use(Meta)` or `ctx.use(Breadcrumbs)`. A slot's pushes are stored under the slot's own segment (`<parent>.@slot`), separate from the parent's pushes:

- **Order:** they are collected immediately after the parent segment's pushes and before any child route's. A route's `@meta` slot therefore comes after every layout above it, and a layout-level slot comes before the routes it wraps.
- **Lifecycle:** they are present while the slot is mounted with its parent and removed when it unmounts.
- **Partial updates:** a slot-only revalidation replaces just the slot's pushes; the parent's pushes stay intact.

A UI-less `@meta` slot keeps metadata out of the route handler:

```tsx
import { Meta } from "@rangojs/router";

// The layout sets defaults via a title template
layout(
  (ctx) => {
    ctx.use(Meta)({ title: { template: "%s | Store", default: "Store" } });
    return <StoreLayout />;
  },
  () => [
    path("/:slug", ProductPage, { name: "product" }, () => [
      parallel({
        "@meta": async (ctx) => {
          const product = await ctx.use(ProductLoader);
          const meta = ctx.use(Meta);
          meta({ title: product.name });
          meta({ name: "description", content: product.description });
          return null; // UI-less slot, only sets metadata
        },
      }),
    ]),
  ],
);
```

The route's slot pushes after the layout, and `Meta` keeps the last value per key, so the per-route title beats the layout default. See [Metadata](/docs/rango/features/metadata).

For metadata derived from a loader, you can skip the slot: a loader body can push `Meta` and `Breadcrumbs` itself with the same `ctx.use(Handle)` call. Keep the `@meta` slot for metadata that is not loader-derived, such as templates, static descriptions, or structured data with independent inputs.

## Self-contained slots via handler.use

The slot handler can carry its own loader, skeleton, and revalidation via `.use`. Every mount site then declares just the slot name:

```tsx
import { loader, loading, revalidate, type Handler } from "@rangojs/router";
import { revalidateCartData } from "./revalidation-contracts";

const CartSummary: Handler = async (ctx) => {
  const cart = await ctx.use(CartLoader);
  return <CartSummaryView cart={cart} />;
};
CartSummary.use = () => [
  loader(CartLoader),
  loading(<CartSkeleton />),
  revalidate(revalidateCartData),
];

// Same slot in two layouts, no copy-pasted plumbing.
layout(<DashboardLayout />, () => [
  parallel({ "@cart": CartSummary }),
  path("/dashboard", DashboardIndex, { name: "dashboard.index" }),
]);

layout(<AccountLayout />, () => [
  parallel({ "@cart": CartSummary }),
  path("/account", AccountIndex, { name: "account.index" }),
]);
```

Slots have the narrowest `handler.use` allow-list: only `revalidate`, `loader`, `loading`, `errorBoundary`, `notFoundBoundary`, and `transition`. No middleware, no layout. See [handler.use](/docs/rango/guides/handler-use).

## Scoping explicit use(): broadcast vs slot-local

The shared `use()` callback in `parallel({...}, () => [...])` runs **once per slot**, so every item lands on every slot. That's right for accumulating items (`loader`, `revalidate`, `errorBoundary`, `notFoundBoundary`, `transition`). But `loading()` is single-assignment, so broadcasting it overwrites every slot's `handler.use` default. For per-slot precision, pass a **slot descriptor** `{ handler, use }`:

```tsx
// @cart gets a custom skeleton; @notifs keeps its handler.use default.
parallel({
  "@cart": {
    handler: Cart,
    use: () => [loading(<CustomCartSkeleton />)],
  },
  "@notifs": Notifs,
});

// Opt one slot out of streaming while siblings still stream the broadcast.
parallel(
  {
    "@cart": { handler: Cart, use: () => [loading(false)] },
    "@notifs": Notifs,
  },
  () => [loading(<BroadcastSkeleton />)],
);
```

Per-slot merge order is **handler.use, then shared use, then slot-local use**. Slot-local is the narrowest scope and wins for last-write-wins items.

Both a bare arrow slot handler (`"@cart": (ctx) => ...`) and an arrow inside a descriptor (`handler: (ctx) => ...`) infer their `ctx` type; no annotation is needed.

## Slot overrides: last definition wins

When multiple `parallel()` calls define the same slot name, the last definition wins and earlier definitions of that slot are removed. Other slots from the earlier call are preserved:

```tsx
layout(DashboardLayout, () => [
  parallel({
    "@sidebar": () => <DefaultSidebar />,
    "@footer": () => <Footer />,
  }),

  // Override just @sidebar; @footer is preserved
  parallel({ "@sidebar": () => <CustomSidebar /> }),

  path("/", DashboardIndex, { name: "index" }),
]);
```

The override takes the whole slot, including that call's `use()` items (loaders, loading, revalidate); the first call's items for `@sidebar` are gone. This is how a mount site replaces a slot that a shared factory or a handler's `.use` defined.

## Revalidation

Where the slot sits decides its default once it is on screen (the first render always happens):

| Slot declared under                     | Navigation                           | Action     |
| --------------------------------------- | ------------------------------------ | ---------- |
| a `path()` or one of its orphan layouts | re-renders when params/search change | re-renders |
| a standalone `layout()`                 | kept                                 | kept       |

A route-scoped slot belongs to the route entry, so handler-set data stays consistent with no configuration. A layout-level slot is kept unless a `revalidate()` opts it in:

```tsx
import * as CartActions from "./actions/cart";

parallel({ "@cart": () => <CartSummary /> }, () => [
  loader(CartLoader),
  revalidate((ctx) => ctx.isAction(CartActions) || undefined),
]);
```

A `revalidate()` in the slot's `use()` decides whether the **slot component** re-renders. It does not gate the slot's loaders: each `loader()` is revalidated separately, with its own `revalidate()` items and the loader defaults (loaders re-run after every action by default). To scope a loader, give it its own rule, as in `loader(CategoriesLoader, () => [revalidate(() => false)])`.

A `revalidate()` callback may return a hard `boolean`, a soft `{ defaultShouldRevalidate }` object, or nothing (`void` / `null` / `undefined`) to defer to the next revalidator. It is the same contract as `loader()`, `path()`, and `layout()`; see [Loaders](/docs/rango/features/loaders). Callbacks must be synchronous: a returned Promise is ignored and dev logs a warning.

`revalidate()` decides whether to _re_-render a slot, never whether to render it the first time. A slot the browser has not rendered yet always renders, so `revalidate(() => false)` means "render once, then keep", never "don't appear".

In either position, revalidating only the parallel does not re-run outer handlers or layouts. If the slot reads `ctx.get()` data established above it, put the same named revalidation contract on both the producer and the slot:

```tsx
import type { Revalidate } from "@rangojs/router";
import * as CartActions from "./actions/cart";

export const revalidateCartData: Revalidate = (ctx) =>
  ctx.isAction(CartActions) || undefined;

layout(CartLayout, () => [
  revalidate(revalidateCartData), // producer reruns
  parallel(
    { "@cart": CartSummary },
    () => [revalidate(revalidateCartData)], // consumer reruns
  ),
]);
```

## Pitfalls

- **A route-scoped slot without `loading()` can blank the route.** A slot under a `path()` re-renders on any params or search change, including query-only navigations (`?tab=...`) its content doesn't depend on. With no `loading()` of its own, that refresh suspends at the route's `loading()` and replaces the whole route with its skeleton. Give the slot its own `loading()`, or scope its `revalidate()` with the route's named contract. A bare `revalidate(() => false)` goes too far: the slot then keeps the previous param's content on a product-to-product navigation.
- **Slot-level `transition()` is not applied at render time.** The item is allowed in the slot allow-list, but only layout and route wraps take effect. For a modal-only or slot-only morph, use an element-level React `<ViewTransition>` inside the slot's component. Conversely, a layout-level `transition()` fires when the layout's default outlet content changes but **not** when a `<ParallelOutlet />` mounts new content. See [View Transitions](/docs/rango/guides/view-transitions).
- **Under a shared artifact** (`cache()`, `"use cache"`, a PPR shell), a server-side `await ctx.use(CartLoader)` in the slot is baked in: the value at capture time freezes into the artifact. Consume the loader client-side (`useLoader` in a `"use client"` component) to keep the slot live per request. See [use cache](/docs/rango/guides/use-cache) and [PPR](/docs/rango/guides/ppr).
- **Broadcast `loading()` clobbers slot defaults.** A single `loading()` in the shared `use()` lands on every slot. Scope it with the slot descriptor form.
