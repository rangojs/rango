description: Cache a page's rendered HTML shell and serve it instantly while the live parts resume on every request.

---

You have a page whose frame is stable — layout, headings, product copy — but parts of it must stay fresh on every request: a price, a basket badge, reviews. PPR caches the rendered HTML shell of the page (the React `prerender` prelude bytes plus `postponed` state) and, on later requests, flushes those bytes after route classification and the complete middleware chain, but before downstream tail rendering. It then resumes just the live holes. The browser sees one ordinary streamed document; loaders stay fresh on every request.

This is in-function PPR on every deployment target: the worker or function serves the stored prelude, not a CDN static file. An ordinary `ppr` route captures its shell in the background after a runtime MISS. Combine [Prerender](/docs/rango/guides/prerender) with the `ppr` path option to produce the shell during `vite build` and make the first production request a shell HIT.

**Which cache layer?** PPR sits between the segment cache and the whole-response cache:

- [`cache()`](/docs/rango/features/caching) caches rendered Flight segments (a cached shell with live loader holes), but HTML is still rendered on every request. `ppr` is the path option that caches the rendered HTML itself, and it treats the handler layer the way `cache()` does: a shell HIT replays the handler output the capture recorded and never runs a handler. A `ppr` route may be uncached, fully `cache()`d, or mixed.
- [`"use cache"`](/docs/rango/guides/use-cache) caches one function's value; inside a shell it is pinned at capture time.
- [Prerender](/docs/rango/guides/prerender) fills the segment cache at build time; with `ppr` it also bakes the shell.
- The [Document Cache](/docs/rango/guides/document-cache) freezes the whole response, loader output included — use it instead when nothing needs to stay live.

## Opt in with the `ppr` path option

PPR is declared on the page route. Serving is integral to the router — there is nothing to mount. The only prerequisite is an app-level `createRouter({ cache })` store that implements the shell family (`getShell`/`putShell`). All built-in stores do: `MemorySegmentCacheStore` (dev/tests), `CFCacheStore` (Cloudflare Cache API, plus KV when configured), and `VercelCacheStore` (Vercel Runtime Cache). A `ppr` route on a store without the family keeps rendering normally, with a once-per-key warning.

```tsx
import { createRouter, urls } from "@rangojs/router";
import { CFCacheStore } from "@rangojs/router/cache";

export const urlpatterns = urls(({ path, layout, loader, loading }) => [
  layout(ProductShell, () => [
    path(
      "/products/:id",
      PricePage,
      // `ppr` is the whole opt-in AND the policy. `ppr: true` uses the default
      // ttl (300s); an object sets ttl/swr/tags (PartialPrerenderProps).
      { name: "product", ppr: { ttl: 600, swr: 120 } },
      () => [
        loader(LivePriceLoader),
        loading(<PriceSkeleton />), // structural hole: the loader subtree stays live
      ],
    ),
  ]),
]);

export const router = createRouter<AppBindings>({
  document: Document,
  urls: urlpatterns,
  cache: (env, ctx) => ({
    store: new CFCacheStore({ kv: env.CACHE_KV, ctx: ctx! }),
  }),
});
```

A route without `ppr` pays zero cost: no store read, no capture, no logs. `ppr` is per page route — declaring it on a layout is not supported. The shell is keyed per host + pathname + sorted search, shared across all users — which is exactly why the identity rules below exist.

Each distinct key is a capture and a stored shell of its own, so keep what varies it to a small, known set. Query strings count: a product page reached as `/products/1?color=red&size=m` and `/products/1?color=blue&size=m` has one shell per distinct query, and a tracking param a link appends (`utm_*`, a click id) mints another. [`cache.searchParams`](/docs/rango/reference/create-router#cache) on `createRouter` drops params from the key (`{ exclude: TRACKING_SEARCH_PARAMS }`, or an `{ include: [...] }` allowlist); exclude only a param the shell does not render from, or the first variant captured is served for every value of it. The same holds for request partitions (the route's `cache({ key })` or the store's `keyGenerator`, see [Per-user data](#per-user-data)): normalize what the key reads to the values you serve.

## What counts as a hole

Holes are render-defined — decided by the shape of your tree, not by configuration. Two classes:

| Class          | What decides it                                                                                                                                                                                                                                                                                        | At capture                                                           | At serve (HIT)                                  |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------- | ----------------------------------------------- |
| **Structural** | a live-lane loader (no `ssr: false`) read under a boundary: `loading()` (the whole segment subtree under it) or an inline `<Suspense>` above the reader                                                                                                                                                | live loaders masked; the fallback bakes in as route structure        | loaders run fresh; resume fills it              |
| **Shell**      | everything the handler layer produces — awaited data, a promise passed as a prop (even under `<Suspense>`), an async server component, handle pushes at any depth, a loader the handler awaits — plus replayed `cache()` segments and the settled non-promise data of bake-lane (`ssr: false`) loaders | awaited (bounded by `ppr.captureTimeout`) and baked into the prelude | served from the frozen prelude; no handler runs |

One hole lives inside loader data, decided by shape: a promise nested in a bake-lane loader's return value, or in a handle container a loader pushes, is masked at capture however fast it settles and becomes a hole at the consumer's own `<Suspense>`. The rule for promises, by producer: **a promise a handler produces bakes, at any depth; a promise nested in loader data stays live.**

### Handler output always bakes

A promise the handler passes to a component under `<Suspense>` is not a hole. The capture waits for it and bakes the settled value, which every HIT then serves for the shell's lifetime:

```tsx
function ProductPage(ctx: HandlerContext) {
  const reviews = fetchReviews(ctx.params.id); // not awaited here, but the capture awaits it
  return (
    <main>
      <h1>Product {ctx.params.id}</h1> {/* shell */}
      <ReviewsSection promise={reviews} />{" "}
      {/* shell too: the capture's reviews, on every HIT */}
    </main>
  );
}
```

The same holds for an async server component (with or without `<Suspense>` above it), a promise nested in a handle the handler pushes, and a loader the handler awaits with `ctx.use()`. The capture waits for all of it within one deadline, `ppr.captureTimeout` (15 seconds by default); handler output that has not settled by then stores no shell, and a once-per-key warning says it "did not settle within ppr.captureTimeout". A shell HIT never runs a handler — it replays the handler output the capture recorded — so nothing on a HIT could produce a fresh value for a handler promise.

To keep a region fresh per request, load it in a loader without `ssr: false` and read it with `useLoader` under `loading()` or an inline `<Suspense>`. Inside an `ssr: false` loader, return the live part as a nested promise (next section).

### Migrating from the old promise-hole model

Earlier versions treated a pending handler promise under `<Suspense>` as a hole and re-ran handlers on some HITs. That is gone:

Everything a handler produces is shell material, as it is under `cache()`: a promise it passes to a component under `<Suspense>`, an async server component, a nested promise in a handle it pushes, and a loader it awaits are all awaited at capture (bounded by `ppr.captureTimeout`) and served frozen for the shell's lifetime. A HIT never runs a handler. To keep a value fresh per request, load it in a loader without `ssr: false` and read it with `useLoader` under `loading()` or an inline `<Suspense>`; inside an `ssr: false` loader, return that part as a nested promise. Request-scoped reads the capture now waits for refuse it: `cookies()`, `headers()`, a `{ cache: false }` variable, and `ctx.dynamic()` inside a handler promise, an async component, a handle push, or a loader a handler awaits. A normal `ctx.get()` value is not guarded: shell material is shared per host+URL. `cache(false)`, or a `condition()` that returns false, on a `ppr` route now renders the request like a cache miss (no shell).

### Loaders: `ssr: false` picks the lane

Among the loaders a route registers, only `loader(Def, { ssr: false })` bakes into the shell, and only the parts of its returned data that are not promises. The loader runs at capture, and its settled non-promise values are frozen into the shell (pinned per shell). Any promise inside the returned data is masked at capture and stays a live hole, streamed fresh on every request at the consumer's own `<Suspense>`, however fast it settles. The shape of the return value declares what is live: a plain value bakes, and a promise stays live. (A loader a handler awaits with `ctx.use()` is handler output: the handler's copy bakes whatever the flag says.) `ssr: false` on a loader is the same knob as `loading(fallback, { ssr: false })`: the document does not stream a fallback for it but resolves the loader before the first flush, so under `ppr` its value lands in the prelude and bakes into the shell. See [Loaders](/docs/rango/features/loaders) for the delivery details.

- Promises are found at any depth inside plain objects, arrays and JSX props: `{ items: [{ stock: fetchStock(sku) }] }` keeps every `stock` live. A `Map`, `Set`, class instance, or other non-plain object is a leaf — a promise inside it is not masked and does not become a live hole. Keep live promises in plain objects, arrays and JSX props.
- JSX in the returned data bakes like any other value. A promise in the props of a host element, `<Suspense>` or a client component (`<p>{fetchStock(sku)}</p>`) is the hole, and the rest of that JSX stays baked on every hit. A server component with a promise anywhere in its props (`<Reviews data={fetchReviews(id)} />`) is a hole as a whole: on a hit it renders from the fresh loader run, so whatever it renders outside its own `<Suspense>` must come out the same on every run.
- The consumer reads a live property with `use(data.price)` inside its own `<Suspense>`. That boundary is the hole.

Every loader without `ssr: false` is entirely live, whether or not it has `loading()`: masked at capture, postponed at its boundary, and streamed fresh on every request, no matter how fast it resolves. It needs a boundary — `loading()` or an inline `<Suspense>` above the reader — or the shell is refused: a masked read with no boundary above it leaves nothing to freeze, the capture is refused with a once-per-key warning, and the route keeps serving MISSes. A route whose loaders are all `ssr: false` needs no `loading()`: nothing is masked, and the shell captures complete. So `loading()` is not the lane switch; it is one of the two boundary kinds a live loader needs.

```tsx
export const ProductLoader = createLoader(async (ctx) => {
  const product = await getProduct(ctx.params.id);
  return {
    name: product.name, // plain value: bakes
    description: product.description, // plain value: bakes
    price: fetchPrice(ctx.params.id), // promise: masked at capture, live hole
  };
});

path("/products/:id", ProductPage, { name: "product", ppr: true }, () => [
  loader(ProductLoader, { ssr: false }), // bake lane
  loader(StockLoader), // live lane: ProductPage reads it under an inline <Suspense>
]);
```

```tsx
// ProductDetails.tsx — the consumer of the live nested property.
"use client";
import { Suspense, use } from "react";
import { useLoader } from "@rangojs/router/client";

function Price({ price }: { price: Promise<number> }) {
  return <PriceTag amount={use(price)} />;
}

export function ProductDetails() {
  const { data } = useLoader(ProductLoader);
  return (
    <article>
      <h1>{data.name}</h1> {/* baked */}
      <p>{data.description}</p> {/* baked */}
      <Suspense fallback={<PriceSkeleton />}>
        <Price price={data.price} /> {/* hole — fresh on every request */}
      </Suspense>
    </article>
  );
}
```

`name` and `description` are frozen into the shell; `price` is a hole under the consumer's `<Suspense>`, fresh on every request. `StockLoader` is masked at capture and postpones at the inline `<Suspense>` around its reader.

On a shell HIT, a bake-lane loader whose return had no promises is served from the container pinned at capture, and its body does not run: a HIT is rendered from the shell, like the handlers it replays, so the loader costs nothing per HIT and its output changes only when the shell is recaptured (TTL/SWR expiry or tag invalidation). Side effects in its body (logging, counters, writes) happen once per capture, not per request. A return that carries promises runs on every HIT instead, because only its body can create the live promises that fill the holes; the baked parts are overlaid onto the fresh result so the payload matches the frozen shell. Give such a loader its own cache, `loader(Def, { ssr: false }, () => [cache({ ttl })])`, so that run reads through it. A client navigation that replays the shell (`x-rango-ppr-replay: HIT`) matches the document HIT: a promise-free loader is served from its pin without running, and a loader whose return had promises runs with its baked parts pinned over the fresh result. That includes an `ssr: false` loader on an entry that also has `loading()`. Before, a navigation ran every loader and served its fresh values.

Whether a return "has promises" is decided once, at capture, by the shape of the value, not by timing: the capture walks the returned data through plain objects, arrays and JSX element props, turns every promise it finds into a hole, and stores the result with the shell. A promise that resolves in 1 ms is still a hole, so `{ product: await getProduct() }` bakes and does not run on a HIT, while `{ product: getProduct() }` is a hole and runs on every HIT. A promise inside a `Map`, `Set` or class instance is not walked and is not a hole: the capture waits for it and bakes its settled value, and a HIT serves that value without running the loader.

The granularity is the whole loader: a bake-lane loader returning `{ product, reviews: promise }` runs its entire body on every HIT, the product fetch included, even though the captured product is what the page shows. Split it into a promise-free `ssr: false` loader and a live loader for the per-request part, or give it its own `cache()` so that run reads through it:

```tsx
loader(ProductLoader, { ssr: false }), // promise-free: baked, not run on a HIT
loader(ReviewsLoader),                 // live: the hole, under loading()
```

The settled handle pushes of a bake-lane loader, and of the loaders it awaits with `ctx.use()`, are recorded with the shell, because the prelude rendered them. On a HIT they are restored from the shell, so every handle, custom ones included, shows each push once. A loader that does run on the HIT (one returning promises, or a live loader awaiting the same loader) replaces its restored pushes in place with its live ones; a push that lands after the document's handle data was sent reaches the client after hydration. If a capture sees a loader push it cannot record (a promise, or a value holding one), the pinned loaders still run on each HIT, in the background, so that push reaches the page.

The lane is decided per loader, by its own `ssr: false` flag — `loading()` on the same entry, a parent, or a child never changes it. `loading()` only decides where a live loader's hole sits, and it is valid on layout and parallel entries, not just routes. Do not use `loading()` on an app-wide layout as the boundary for its live loaders: any live read without an inline `<Suspense>` of its own suspends to it, the fallback wraps the layout's entire subtree, and your header, nav, and footer fall out of the shell into the skeleton. For guaranteed-fresh widgets under a shared layout, read a live loader under an inline `<Suspense>` in the widget, or use a [parallel slot](/docs/rango/guides/parallel-routes) with its own `loader()` + `loading()` — the chrome bakes and each widget becomes an independent, widget-sized hole. The slot handler must hand the loader to a client component (`useLoader` in a `"use client"` component): that client-side read is the hole. A server-side `await ctx.use(Loader)` in the slot handler is handler output — its value bakes into the shell for every visitor, and if that loader reads `cookies()` or `headers()` the capture is refused.

| Your live region is…                          | Use                                                                                                           |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| data that must be fresh on every serve        | `loader()` (the live lane) + `useLoader` under `loading()` or an inline `<Suspense>`                          |
| loader data, stable container with live parts | `loader(Def, { ssr: false })` (the bake lane), nested promises for live parts                                 |
| handler-fetched data (db, fetch)              | nothing to choose — it bakes, awaited or passed down as a promise; move it into a live loader to make it live |
| handle metadata that must be live             | push it from a loader: a live-lane loader pushes per request; a bake-lane loader's nested promise is a hole   |
| already-resolved / instant values             | `loader(() => Promise.resolve(x))` without `ssr: false`, plus a boundary                                      |
| none of the above                             | nothing — it bakes; that is what the shell is for                                                             |

Handles split by who pushes. A handler's push bakes at any depth: a top-level `ctx.use(H)(promise)` and a nested `ctx.use(H)({ x: promise })` are both awaited at capture and served frozen (keep promises in plain objects, arrays and JSX props; one inside a `Map`, `Set`, or class instance is not waited for, and the capture is refused if it has not settled when the handles are encoded). A loader's push keeps "nesting = liveness": in a bake-lane loader the container settles and bakes, while a nested promise (in plain objects, arrays and JSX props) is masked at capture regardless of timing and streams fresh to the consumer's `<Suspense>` on every HIT. A live-lane loader never runs at capture, so all of its pushes happen per request.

## How a request is served

On a document GET to a `ppr` route the router runs: match, then the **whole middleware chain** (global `router.use()` and route DSL `middleware()`), then the shell lookup. The commit point is after all middleware — any rejection, redirect, or 401 wins before a single shell byte, on MISS and HIT alike, so auth middleware guards PPR for free.

- **HIT** — the stored prelude bytes flush first; segment resolution, the Flight render, and the resume of just the holes run behind them inside the response stream. No handler runs: the handler layer is replayed from the segments the capture recorded, and only loaders run fresh (a promise-free `ssr: false` loader is served from the shell instead).
- **MISS** — a plain live serve, plus a background capture (stampede-guarded, with exponential backoff). Middleware is not re-run during capture; the capture inherits the triggering request's post-middleware context. Handlers run during the capture, and everything they produce settles before the shell is frozen.

| Phase        | MISS        | Background capture                                                                         | HIT                                                                                                    |
| ------------ | ----------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| Middleware   | runs        | not re-run (inherits the request's post-middleware context)                                | runs — the commit point is after it                                                                    |
| Handlers     | run         | run on uncached segments; their promises, async components, and handle pushes settle first | never run — replayed from the capture's recorded segments                                              |
| Live loaders | run fresh   | masked (they are the holes)                                                                | run fresh; resume fills their holes                                                                    |
| `ssr: false` | run fresh   | run; settled non-promise data bakes, nested promises are masked                            | promise-free: served from the shell, not run; returning promises: run, baked parts come from the shell |
| HTML         | full render | `prerender` → stored prelude + postponed state                                             | stored prelude, then `resume` of just the holes                                                        |

A route whose own `cache()` scope refuses the request — `cache(false)`, or a `condition()` that returns false — skips the shell entirely for that document request: it renders like a cache miss, with no `x-rango-shell` header and no capture. Under `ppr`, `cache(false)` means no shell for the route, and a false `condition()` no shell for that request, so a route under a layout's `cache()` cannot be kept out of that `cache()` and still get a shell. If a HIT ever cannot read the shell's recorded segments, it does not run handlers behind the already-sent prelude: it reloads the page once with a `_rsc_shell=miss` query marker, which renders like a cache miss and cannot repeat. The router drops the marker from the request before anything reads it, so middleware, handlers, loaders, cache keys and `useSearchParams` see the URL the visitor asked for, and the browser drops it from the address bar before the page hydrates. When the stored value is corrupt, it also replaces the entry so the next request is a MISS and schedules a recapture; a read that was only slow leaves the entry alone.

The document observability header is `x-rango-shell: HIT | MISS`. Soft
navigations use the captured canonical segment snapshot too: fresh and
stale-within-SWR runtime snapshots replay baked handler output and handles while
loaders stay live. A stale partial read is passive — it does not claim SWR or
recapture HTML; a later document request owns the refresh, and hard expiry falls
open. Partial responses report `x-rango-ppr-replay: HIT; freshness=fresh|stale`
or `BYPASS; reason=<bounded-token>`.

Flight is explicit opt-in with `Accept: text/x-component`; a bare document GET receives HTML. Keeping `Accept: text/html` in a diagnostic command makes the intent explicit:

```bash
curl -s -D - -o /dev/null -H "Accept: text/html" https://app.example.com/products/1 | grep -i x-rango-shell
```

For a runtime-captured route, the first document GET is a `MISS` plus a
background capture; a later request is a `HIT`. For `Prerender + ppr`, the shell
is produced at build time, so the first production request can already be a
`HIT`; in dev the build-time shell capture runs on demand and can return a
`HIT`, but falls open to a `MISS` plus runtime capture when the bounded
foreground wait expires. A route partitioned by `cache({ key })` or a store
`keyGenerator` does not serve its build-time shell (the build captured one
partition); each partition captures at runtime, and a once-per-route warning
says so when a build shell exists. A `keyGenerator` that returns the default
key unchanged partitions nothing and keeps the build shell. A declared route that never flips has an eligibility
problem — look for the once-per-key warning. To catch a refused capture on a
deployment, set `createRouter({ debugShellCapture: true })` (or pass a function
that receives each `ShellCaptureDebugEvent`): a refused attempt reports the
outcome `refused`, and the cause is in the console warning
`Shell capture for "<key>" was refused: …`, logged once per key in each
isolate, production included. Some requests always stay on the normal render
path: non-GET, action/loader fetches, per-request CSP nonce,
`streamMode: "allReady"`, redirects, 404s, error renders, and stores without the
shell family. For bots, `ssr: { resolveStreaming }` returning `"allReady"`
bypasses PPR entirely and serves one complete buffered document. Stored shells
self-invalidate when `React.version` changes, so deploys self-heal via recapture.

### Opting out per request with `ctx.dynamic()`

Middleware and handlers can call `ctx.dynamic()` to keep one request off the shell path. In middleware it runs before the commit point, so the router skips the shell lookup, HIT serving, and MISS capture for that request. In a handler it is too late to avoid the MISS render, but it still prevents the follow-up capture. A call made only during the capture itself (for example inside a handler promise, after an await) refuses that capture. During a `Prerender + ppr` build capture, the same call in middleware skips the baked shell for that URL.

## Options and invalidation

```tsx
path("/products/:id", Page, { name: "product", ppr: true });
path("/products/:id", Page, {
  name: "product",
  ppr: { ttl: 600, swr: 120, tags: ["catalog"] },
});
```

| Field              | Default | Notes                                                                                                                                                                                                      |
| ------------------ | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ttl`              | `300`   | shell freshness window in seconds (`ppr: true` uses the default)                                                                                                                                           |
| `swr`              | —       | stale window: serve the stale shell + background recapture                                                                                                                                                 |
| `tags`             | —       | operational tags unioned with the tags the capture render collects                                                                                                                                         |
| `captureTimeout`   | `15000` | one capture deadline in milliseconds, covering handler output, `ssr: false` loaders, and the prerender; a timed-out capture stores nothing, never a partial shell                                          |
| `maxSnapshotBytes` | 8 MiB   | cap on the pinned `ssr: false` loader data in the entry; the recorded handler layer is exempt. Over it the pins are dropped (the shell is still stored and replayed) and those loaders read the live store |

A shell never outlives the route `cache()` entry it was captured from. Under a route `cache()`, the shell stays fresh no longer than that entry does (and no longer than `ppr.ttl`), and is served, fresh or stale, no longer than that entry can be (and no longer than `ppr.ttl` + `ppr.swr`), so a document request and a client navigation (which reads the `cache()` entry first) show the same handler output. An entry already inside its `swr` window gives a shell that is stale from the start: it is served while a recapture runs, like the entry itself. Each isolate recaptures a stale shell at most once per second: a HIT within a second of the shell's capture serves it without starting another. When the entry a capture read runs out before the capture stores its shell (it was near its end), the capture retries once with a fresh render of the route. No shell is stored when that retry's entry runs out too, when there is no time left in the capture's budget to retry, or when the capture wrote the entry itself and it ran out before the store (its `ttl` + `swr` is no longer than the rest of the capture): the URL then backs off like a refused capture, and a warning names the route and the entry's `ttl` and `swr`, once per route, in dev and production. In dev, an explicit `ppr.ttl` or `ppr.swr` that the entry reduces warns once per route and states the ttl and swr the shell is stored with; with no `ppr` window set, the cap applies silently.

The whole entry — prelude, postponed state, and snapshot — must also fit the store's value limit (25 MiB by default, Cloudflare KV's; `VercelCacheStore` derives its own from its item cap). A bigger entry refuses the capture with a once-per-key warning instead of failing the store write.

`updateTag()`/`revalidateTag()` is the only lever that changes the frozen shell HTML. A captured shell carries the union of the tags recorded while it rendered as shell material — from `cache()` segments, `"use cache"` functions, a render-time `cacheTag()`, and cached loaders on the bake lane (they execute during capture) — plus `ppr.tags`. Invalidating one of those tags drops the shell for a recapture. Live-lane loader tags (every loader without `ssr: false`) never attach; those holes are already live. `revalidate()` is a data lever: it re-renders holes with fresh data but never touches the shell.

`CFCacheStore` and `VercelCacheStore` keep each isolate's last fresh shell read in memory for `memo.shellMs` (default 2000) under `memo.shellMaxBytes` (default 16 MiB), so a warm isolate's next HITs skip the store read. The tag-marker check still runs on every HIT and the isolate that invalidates drops its own copies, so an invalidation is seen on the next request in that isolate. The marker check itself reads through a per-isolate memo, stale-while-revalidate (`memo.markerFreshMs`, default 1000 on `CFCacheStore` and 300 on `VercelCacheStore`; `memo.markerMaxStaleMs`, default 10000 and 2000), so another isolate sees an invalidation once its memoized marker refreshes. Two setups keep an invalidated shell in another isolate's memo until the shell window passes: `CFCacheStore` without KV in purge mode (`tagPurge`), and `VercelCacheStore` in another region (its tag markers are regional) or after a platform `expireTag` issued outside rango. The user who made the change is not served a memoized copy: the response of a request that ran `updateTag()`/`revalidateTag()` sets a fresh-reads cookie (`rango-state-fresh` by default, shared by every router on the host with the same state cookie prefix), and requests carrying it skip both memos on every isolate. Past the memos, each store's own consistency applies. On `VercelCacheStore`, `expireTag` is global (about 300 ms), so that user reads fresh in any region. On `CFCacheStore` with KV, the shell's tag check reads the serving colo's marker (its Cache API copy when `tagCacheTtl` is set, then KV): fresh in the colo that ran the change, while another colo can still serve the old shell until KV propagates the marker there (up to about 60 s) and its cached marker expires. On `CFCacheStore` without KV in purge mode there are no markers: that user sees the change once the purge reaches the colo serving them, and other users can get the purged shell from another isolate's memo until its window passes. Set `memo: { shellMs: 0, markerFreshMs: 0 }` where every user's next request must see the invalidation; with KV, `{ shellMs: 0 }` alone still leaves the marker memo's window. `VercelCacheStore` keeps its memos per `cache` handle, so create the `getCache()` handle once per process ([Deploy to Vercel](/docs/rango/guides/deploy-vercel)).

```ts
new CFCacheStore({ ctx, kv: env.CACHE_KV, memo: { shellMs: 5000 } }); // longer window
new CFCacheStore({
  ctx,
  kv: env.CACHE_KV,
  memo: { shellMs: 0, markerFreshMs: 0 },
}); // memos off, no cookie
```

What the cookie means for your responses:

- It is strictly functional: its value is `1`, it identifies no one, and it only sends that browser's reads past the memos. It is set as `rango-state-fresh=1; Max-Age=<n>; Path=/; HttpOnly; SameSite=Lax`, plus `Secure` on https. `Max-Age` is the longest memo window of the stores the request invalidated plus 1 s, rounded up to whole seconds: 11 on `CFCacheStore` with KV and 3 on `VercelCacheStore` or `CFCacheStore` without KV, at the default `memo`.
- A store with both memos off sets no cookie; that is also the only way to avoid it.
- A response whose request invalidated carries a `Set-Cookie`, so the document cache, a response route's `cache()`, and CDNs that skip responses with cookies do not store it.
- Headers leave with the response: an `updateTag()`/`revalidateTag()` from a streaming loader or render, after the response was handed off, still invalidates but cannot set the cookie (dev warns). Invalidate in a server action, a route handler, or middleware.
- Any client can send the cookie. It only makes that client's own requests read the store, the same cost as turning the memos off, so no rate limit is needed.

These fields govern the in-function shell entry. They do not emit HTTP
`Cache-Control`. If you separately add `s-maxage`, a platform CDN may cache the
completed response — shell, live-hole output, and hydration payload together —
and skip all Rango middleware on a hit. That is valid only for a fully public,
shared response.

## Per-user data

The shell is shared per host + URL across all users (per request partition too, when the route's `cache({ key })` or the store's `keyGenerator` partitions its record: each partition gets its own shell), so identity must never bake. The partition follows nested `cache()` boundaries: a `ppr` route under a `cache()` nested in a keyed one is partitioned by the outer `key()`, composed with the inner one's when it has its own (see [Caching](/docs/rango/features/caching#nested-caches)).

What the guards refuse:

- `cookies()`, `headers()`, and `ctx.get()` of a `{ cache: false }` variable **throw during the capture render**, wherever the capture waits for them: a handler, a promise it passes or pushes, an async server component, a bake-lane loader, and a loader a handler awaits (`await ctx.use(Loader)`). The capture is refused even if your code catches the throw, and the route keeps serving MISSes with a once-per-key warning. `ctx.dynamic()` called there refuses the capture too. Live-lane loaders (every loader without `ssr: false`) are exempt: they never run at capture.
- The guard sees only those reads. A handler or bake-lane loader reading a normal middleware-provided session object (`ctx.get("session")`), or raw request headers, refuses nothing — whatever it renders or returns as plain data is photographed as the capturing user's state. `return { user: session.user }` bakes that user into the shared shell for every visitor. Creating the variable with `createVar({ cache: false })` turns such a read into a refusal instead.
- Inside a bake-lane loader, nested promises are the escape hatch for such data, and they hold regardless of timing: the capture masks every promise nested in a bake-lane container (even an already-resolved `Promise.resolve(null)`), so the consumer's `<Suspense>` becomes a hole that streams the fresh value on every HIT. They are not an escape for `cookies()`/`headers()`: the promise body still runs during capture and trips the guard. A promise in handler output is no escape at all — it bakes.
- Rule of thumb: per-user data on a PPR page lives in a live-lane loader (no `ssr: false`) consumed client-side with `useLoader` under `loading()` or an inline `<Suspense>`, or in a nested promise in bake-lane loader data.

## Pitfalls

- **Handler and loader header writes throw.** On a `ppr` route only middleware writes response headers. A handler or loader calling `ctx.headers.set()`, `cookies().set()`, `ctx.setTheme()`, or the request-context `header()`/`setStatus()` throws on every render: handlers never run on HITs (their output is replayed, so the write would differ between MISS and HIT), and loaders settle after the shell's headers have flushed. Move the write into route middleware, which runs on every request including HITs. The one exception: a handler that calls `ctx.dynamic()` first may write its own headers, because that render never HITs.
- **A pending handler promise expected to be a hole** — it is not. A promise the handler passes under `<Suspense>`, an async server component, or a promise nested in a handler's handle push is awaited at capture and served frozen on every HIT. Move per-request data into a live-lane loader read with `useLoader` under `loading()` or an inline `<Suspense>`.
- **A request-scoped read the capture waits for** (`cookies()`, `headers()`, a `{ cache: false }` variable, `ctx.dynamic()`) — the capture is refused (warned once per key) and the route keeps serving MISSes. Move the read onto the live lane: a loader without `ssr: false`, read under `loading()` or an inline `<Suspense>`.
- **A loader a handler awaits (`await ctx.use(Loader)`) that reads `cookies()` or `headers()`** — refuses the capture like any other read the capture waits for: every request is `x-rango-shell: MISS`, and the warning names the loader. Register the loader with `loading()` and read it with `useLoader` instead. On a route without `ppr`, `cache()` still allows it.
- **A bake-lane container that must be fresh per document GET** — it is snapshot-pinned for the shell's lifetime by design. Use the live lane (drop `ssr: false`) or a nested promise.
- **Handler output or a bake-lane loader slower than `ppr.captureTimeout` (15s by default)** — the capture stores nothing rather than a partial shell. Make the slow part cheaper with `cache()`/`"use cache"`, move it into a live loader, or raise the budget.
- **`cache(false)` or a false `condition()` on a `ppr` route** — the document request renders like a cache miss: no shell, no `x-rango-shell` header, no capture.
- **Shell shows capture-time data for the shell's lifetime** — a `cache()`/`"use cache"` value baked into the shell is pinned at capture and replayed on every HIT, even after that cache entry expires or is recomputed. Parity beats freshness inside the shell. Tags are the link back: the tags that entry carried ride the shell, so `updateTag()` on one drops the shell too; an untagged entry has no such link. If a region needs freshness, put it under a hole, or tag the shell (tag the cached read, call `cacheTag()` in shell render code, or add `ppr.tags`).
- **Uncached values in server output are frozen, not drifting** — a raw `Date.now()`/`Math.random()`/uncached `fetch` in a handler or server component renders once per capture, and the prelude and every HIT show that value for the shell's lifetime. Move it under a hole if it must change per request. A client component rendering such a value during SSR still mismatches on hydration, as on any SSR page.
- **Stacking with the Document Cache or an HTTP CDN cache** — both cache the completed composite, including live-hole output, so PPR is redundant on a hit. An external CDN also bypasses every Rango middleware.
- **Per-request CSP nonce** — supply it via `createRouter({ nonce })`, the canonical path; a nonced route serves the normal render path with a once-per-key warning (a shared shell cannot bake one request's nonce).
- **HIT status commits at the flush** — a failing hole cannot become a 500/redirect after the first shell byte; error UI renders inline via Suspense/error boundaries, like any streamed SSR page.
