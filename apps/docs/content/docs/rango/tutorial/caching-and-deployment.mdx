**Where we are:** Brew reads stock and the cart through loaders and writes the cart through a server action, but every request still renders the whole tree from scratch.

The shop pages barely change between requests, so let's cache them. The key idea in Rango: `cache()` caches **everything except loaders**. On a hit, the cached segments (layouts, route components) are served from the store, while loaders re-run fresh on every request and stream into the same response. Cached UI plus live data, in one streamed response.

## Wire a cache store

`cache()` needs a store; without one, cache boundaries render live. On Cloudflare Workers that is `CFCacheStore`, built on the Cache API with an optional KV namespace as a second tier. The KV namespace also holds the markers that tag invalidation uses later in this part, so add it now. Declare the binding in `wrangler.json`:

```jsonc
// wrangler.json
{
  "name": "brew",
  "main": "./src/worker.ts",
  "compatibility_date": "2025-10-01",
  "compatibility_flags": ["nodejs_compat", "nodejs_als"],
  "assets": {
    "directory": "./dist/client",
  },
  "kv_namespaces": [
    {
      "binding": "CACHE_KV",
      "id": "replace-with-your-namespace-id",
    },
  ],
}
```

Local development simulates KV, so the placeholder id works until you deploy. Before deploying, create the namespace with `pnpm exec wrangler kv namespace create CACHE_KV` and paste the id it prints.

The store needs the per-request `ExecutionContext` to schedule non-blocking writes, so the router takes the cache config as a function of `(env, ctx)`:

```tsx
// src/router.tsx
import { createRouter } from "@rangojs/router";
import { CFCacheStore } from "@rangojs/router/cache";
import { Document } from "./document";
import { urlpatterns } from "./urls";

export const router = createRouter({
  document: Document,
  urls: urlpatterns,
  cache: (env, ctx) => ({
    store: new CFCacheStore({
      ctx: ctx!,
      kv: env.CACHE_KV,
      defaults: { ttl: 300 },
    }),
  }),
});
```

The `ctx` here is the `ExecutionContext` your worker already passes via `router.fetch(request, { env, ctx })`, so there is nothing to change in `src/worker.ts`. It is typed optional on the factory, hence the `!`.

## Cache the shop segments

Wrap the shop group in a `cache()` boundary, and give the product route its own nested boundary with tags. An inner boundary overrides the outer one's settings for its subtree:

```tsx
// src/urls.tsx
import { urls } from "@rangojs/router";
import * as CartActions from "./actions/cart";
import { ShopLayout } from "./layouts/shop-layout";
import { CartLoader } from "./loaders/cart";
import { StockLoader } from "./loaders/stock";
import { HomePage } from "./pages/home";
import { ProductPage, ProductSkeleton } from "./pages/product";
import { ShopPage } from "./pages/shop";

export const urlpatterns = urls(
  ({ path, layout, loader, loading, revalidate, cache }) => [
    path("/", HomePage, { name: "home" }),

    cache({ ttl: 300 }, () => [
      layout(<ShopLayout />, () => [
        loader(CartLoader, () => [
          revalidate((ctx) =>
            ctx.isAction() ? ctx.isAction(CartActions) : undefined,
          ),
        ]),
        path("/shop", ShopPage, { name: "shop" }),
        cache(
          {
            ttl: 300,
            tags: (ctx) => [`product:${ctx.params.slug}`, "products"],
          },
          () => [
            path("/shop/:slug", ProductPage, { name: "product" }, () => [
              loader(StockLoader),
              loading(<ProductSkeleton />),
            ]),
          ],
        ),
      ]),
    ]),
  ],
);
```

For five minutes, the rendered layout and pages are served from the cache. `StockLoader` and `CartLoader` are the live holes: they still run on every request. Reload a product page a few times. The shell is a cache hit, yet the stock number keeps wobbling, because the loader (with its deliberate randomness from part 4) re-resolved each time. And the cart badge shows _your_ count even though the shell is shared.

This is where the discipline from parts 4 and 5 pays off:

- `CartLoader` reads `cookies()`, which is allowed because it is a loader. Reading `cookies()` directly in a handler inside a `cache()` boundary throws, precisely so one user's data cannot be frozen into the shared entry.
- Both loaders are consumed with `useLoader()` in client components. Awaiting `ctx.use(StockLoader)` in the handler and rendering the result would bake one request's stock into the cached shell served to everyone.

## Bust the product cache from the action

The product boundary tags each cached entry with `product:<slug>` and `products`, and tags can be invalidated on demand. Bust the tag from the mutation that touches the product. Brew has no product-editing flow yet, but the wiring is the point, so add it to `addToCart`:

```ts
// src/actions/cart.ts
"use server";

import { cookies, updateTag } from "@rangojs/router";

export type CartState = { added?: string } | null;

function readCart(): string[] {
  const raw = cookies().get("cart")?.value;
  if (!raw) return [];
  try {
    return JSON.parse(raw) as string[];
  } catch {
    return [];
  }
}

export async function addToCart(
  _prev: CartState,
  formData: FormData,
): Promise<CartState> {
  const slug = formData.get("slug") as string;
  const cart = readCart();
  cart.push(slug);
  cookies().set("cart", JSON.stringify(cart), { path: "/" });

  // Evict this product's cached segment. Awaiting gives read-your-own-writes:
  // the action's re-render and the next navigation see fresh output.
  await updateTag(`product:${slug}`);
  return { added: slug };
}
```

There are two invalidation verbs, both variadic, both imported from `@rangojs/router`:

| API                      | Timing                      | Use in                    |
| ------------------------ | --------------------------- | ------------------------- |
| `updateTag(...tags)`     | awaitable (`Promise<void>`) | server actions            |
| `revalidateTag(...tags)` | background, non-blocking    | route handlers / webhooks |

On `CFCacheStore`, tag invalidation needs the `kv` namespace you wired above (or the `tagPurge` purge mode). With neither, invalidation logs a warning and has no effect.

## A JSON endpoint for products

Storefronts grow API consumers. Response routes skip the RSC pipeline entirely and return plain `Response`s. Add one at the top level of the `urls()` array, and the imports it needs:

```tsx
// src/urls.tsx
import { RouterError, urls } from "@rangojs/router";
import * as CartActions from "./actions/cart";
import { PRODUCTS } from "./data";
import { ShopLayout } from "./layouts/shop-layout";
import { CartLoader } from "./loaders/cart";
import { StockLoader } from "./loaders/stock";
import { HomePage } from "./pages/home";
import { ProductPage, ProductSkeleton } from "./pages/product";
import { ShopPage } from "./pages/shop";

export const urlpatterns = urls(
  ({ path, layout, loader, loading, revalidate, cache }) => [
    path("/", HomePage, { name: "home" }),

    cache({ ttl: 300 }, () => [
      layout(<ShopLayout />, () => [
        loader(CartLoader, () => [
          revalidate((ctx) =>
            ctx.isAction() ? ctx.isAction(CartActions) : undefined,
          ),
        ]),
        path("/shop", ShopPage, { name: "shop" }),
        cache(
          {
            ttl: 300,
            tags: (ctx) => [`product:${ctx.params.slug}`, "products"],
          },
          () => [
            path("/shop/:slug", ProductPage, { name: "product" }, () => [
              loader(StockLoader),
              loading(<ProductSkeleton />),
            ]),
          ],
        ),
      ]),
    ]),

    path.json(
      "/shop/:slug",
      (ctx) => {
        const product = PRODUCTS.find((p) => p.slug === ctx.params.slug);
        if (!product) {
          throw new RouterError("NOT_FOUND", `No product: ${ctx.params.slug}`, {
            status: 404,
          });
        }
        return product;
      },
      { name: "productJson" },
    ),
  ],
);
```

The handler returns plain data, which is serialized as-is on success. A thrown `RouterError` becomes an RFC 9457 `application/problem+json` body, so consumers branch on `res.ok`. The pattern is the same `/shop/:slug` the product page uses: when routes share a URL pattern, the router merges them and picks one by the `Accept` header. Browsers still get the page, and API clients asking for JSON get the product:

```bash
curl -H "Accept: application/json" http://localhost:5173/shop/burr-grinder
```

Response routes accept only `middleware()` and `cache()` as children. There is no RSC tree, so no loaders or layouts. Details are in [Response Routes](/docs/rango/features/response-routes).

## Ship it

Log in once with `pnpm exec wrangler login`, then build and deploy:

```bash
pnpm exec vite build
pnpm exec wrangler deploy
```

Always deploy right after a build. `vite build` writes the deployable Worker config to `dist/rsc/wrangler.json`, and `wrangler deploy` follows the redirect the build leaves behind. Deploying the source `wrangler.json` without a fresh build does not work, because Wrangler's bundler cannot reconstruct Rango's Vite virtual modules.

On the deployed URL, repeat the experiment from earlier: reload a product page. The shell comes back from the cache while the stock figure keeps changing. The browser cannot tell the shell was cached, because it is one streamed response either way. To watch the store's decisions while you validate, pass `debug: true` to `CFCacheStore` and tail the worker with `pnpm exec wrangler tail`; each cache read logs which tier answered and why.
