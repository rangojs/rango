**Where we are:** an empty directory. By the end of this part, a Rango app serves its first page from the Workers runtime on your machine.

## Install dependencies

Create the project and install the runtime dependencies, then the build and type-checking tooling:

```bash
mkdir brew && cd brew
pnpm init
pnpm add @rangojs/router react react-dom
pnpm add -D vite @vitejs/plugin-react @cloudflare/vite-plugin wrangler typescript @types/react @types/react-dom @cloudflare/workers-types
```

In `package.json`, mark the project as an ES module and add a dev script:

```jsonc
// package.json (add these fields)
{
  "type": "module",
  "scripts": {
    "dev": "vite",
  },
}
```

## TypeScript configuration

Rango's route typing (typed params, names checked at compile time) is plain TypeScript, so give the project a `tsconfig.json`. The `types` entry brings in the Workers runtime types (`ExportedHandler`, `KVNamespace`) and Vite's client types:

```jsonc
// tsconfig.json
{
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "module": "ESNext",
    "moduleResolution": "bundler",
    "jsx": "react-jsx",
    "strict": true,
    "noEmit": true,
    "skipLibCheck": true,
    "isolatedModules": true,
    "types": ["@cloudflare/workers-types", "vite/client"],
  },
  "include": ["src"],
}
```

## Vite configuration

Three plugins, in this order:

```ts
// vite.config.ts
import { cloudflare } from "@cloudflare/vite-plugin";
import { rango } from "@rangojs/router/vite";
import react from "@vitejs/plugin-react";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [
    react(),
    rango({ preset: "cloudflare" }),
    cloudflare({
      configPath: "./wrangler.json",
      viteEnvironment: { name: "rsc", childEnvironments: ["ssr"] },
    }),
  ],
});
```

- `react()` adds React Fast Refresh, so edits to client components update without a full reload. It is optional: `rango()` works without it.
- `rango({ preset: "cloudflare" })` wires the router into Vite's RSC, SSR, and client environments, preconfigured for Workers. It bundles `@vitejs/plugin-rsc`, so there is nothing else to install for RSC.
- `cloudflare()` reads your `wrangler.json` and runs the app in the Workers runtime, so dev traffic goes through your actual Worker, not a Node shim. The `viteEnvironment` block tells it the Worker entry lives in the `rsc` environment with `ssr` as a child; copy it as-is.

## Wrangler configuration

The Worker itself is described by `wrangler.json`:

```jsonc
// wrangler.json
{
  "name": "brew",
  "main": "./src/worker.ts",
  "compatibility_date": "2025-10-01",
  "compatibility_flags": ["nodejs_compat", "nodejs_als"],
  "assets": {
    "directory": "./dist/client",
  },
}
```

`name` is what the Worker will be called when you deploy in part 6, `main` points at the entry file you'll write below, and `assets.directory` is where the client build lands so Cloudflare can serve static files. The two compatibility flags enable the Node APIs the RSC runtime relies on.

## The document shell

Rango renders your entire app inside a `Document` component. It owns the `<html>` element, and every route renders into `children`. The Document must be a client component, and it renders two router components: `<MetaTags />` (the `charset` and `viewport` tags, plus per-route metadata) and `<Scripts />`:

```tsx
// src/document.tsx
"use client";

import type { ReactNode } from "react";
import { MetaTags, Scripts } from "@rangojs/router/client";

export function Document({ children }: { children: ReactNode }) {
  return (
    <html lang="en">
      <head>
        <MetaTags />
        <Scripts />
        <title>Brew</title>
      </head>
      <body>
        <Scripts position="body" />
        {children}
      </body>
    </html>
  );
}
```

## The first route

Routes live in one place: a `urls()` tree, Django-style. Each `path()` takes a pattern, a handler, and a name. Start with a placeholder home page:

```tsx
// src/pages/home.tsx
export function HomePage() {
  return (
    <section>
      <h1>Brew</h1>
      <p>Gear for better coffee.</p>
    </section>
  );
}
```

```tsx
// src/urls.tsx
import { urls } from "@rangojs/router";
import { HomePage } from "./pages/home";

export const urlpatterns = urls(({ path }) => [
  path("/", HomePage, { name: "home" }),
]);
```

The `name` looks redundant right now. It pays off in part 2, when you start generating URLs from route names instead of hardcoding paths.

## The router

`createRouter()` ties the document and the URL tree together. Export it by name as `router`:

```tsx
// src/router.tsx
import { createRouter } from "@rangojs/router";
import { Document } from "./document";
import { urlpatterns } from "./urls";

export const router = createRouter({
  document: Document,
  urls: urlpatterns,
});
```

## The worker entry

Finally, the file `wrangler.json` points at. Every request that reaches the Worker is handed to `router.fetch()`, which matches the URL, renders, and returns the response. Pass `env` and `ctx` through so route handlers can reach your Cloudflare bindings, and so the cache store in part 6 can schedule background writes:

```ts
// src/worker.ts
import { router } from "./router";

export default {
  fetch(request, env, ctx) {
    return router.fetch(request, { env, ctx });
  },
} satisfies ExportedHandler;
```

Don't shorten this to `export default { fetch: router.fetch }`. Workers call `fetch(request, env, ctx)`, while `router.fetch` takes `(request, { env, ctx })`, so the bindings would be lost.

## Run it

```bash
pnpm dev
```

Open `http://localhost:5173`. You should see the Brew heading: server-rendered React, served by a Cloudflare Worker running locally. That's the whole skeleton. `urls.tsx` will grow as the app does, while `router.tsx`, `document.tsx`, and `worker.ts` barely change again.
