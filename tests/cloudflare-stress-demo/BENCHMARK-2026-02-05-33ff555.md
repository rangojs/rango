# Prefix Short-Circuit Optimization Benchmark

Performance benchmark for the prefix-based short-circuit optimization in `@rangojs/router`.

- **Date**: 2026-02-05
- **Base Commit**: `33ff555` (optimization changes uncommitted)
- **Deployed Version**: `b0112815-cf85-4682-a406-abecff58b920`

## Problem Statement

With 14,000+ routes, route matching was taking ~200ms for worst-case routes. The router was checking every single route pattern sequentially, even when entire groups of routes could be ruled out based on URL prefix.

For example, a request to `/api/users/123` was checking all 9,000+ `/site/:locale/*` routes before even reaching the `/api/*` routes.

## Solution: Prefix-Based Short-Circuit Optimization

Routes grouped by `include()` prefix are now stored in separate `RouteEntry` objects with a pre-computed `staticPrefix`. During route matching, entries are skipped entirely if the pathname doesn't start with the entry's `staticPrefix`.

### How It Works

**Before (all routes in one entry):**

```
RouteEntry {
  prefix: "",
  routes: { all 14,000 routes flattened }
}
```

Every request checks all 14,000 routes sequentially.

**After (separate entries per include prefix):**

```
RouteEntry { prefix: "", staticPrefix: "", routes: { 3 root routes } }
RouteEntry { prefix: "", staticPrefix: "/site", routes: { 5,003 site routes } }
RouteEntry { prefix: "", staticPrefix: "/api", routes: { 5,002 API routes } }
```

Request to `/api/*` → skip entry with `staticPrefix="/site"` → save 5,003 route checks!

## Implementation Details

### 1. Added `staticPrefix` to RouteEntry (`types.ts`)

```typescript
export interface RouteEntry<TEnv = any> {
  prefix: string;
  /**
   * Pre-computed static prefix for fast short-circuit matching.
   * Examples:
   * - "/api" → staticPrefix = "/api"
   * - "/site/:locale" → staticPrefix = "/site"
   * - "/:locale" → staticPrefix = "" (empty, can't optimize)
   */
  staticPrefix: string;
  routes: ResolvedRouteMap<any>;
  // ...
}
```

### 2. Added `extractStaticPrefix()` function (`pattern-matching.ts`)

Extracts the static portion of a pattern before any dynamic segments:

```typescript
export function extractStaticPrefix(pattern: string): string {
  if (!pattern || pattern === "/") return "";

  // Find the first occurrence of : or *
  const paramIndex = pattern.indexOf(":");
  const wildcardIndex = pattern.indexOf("*");

  // Find everything before the first param/wildcard
  // "/site/:locale" → "/site"
  // "/api" → "/api"
  // "/:locale" → ""
}
```

### 3. Added `patternsByPrefix` Map (`context.ts`, `urls.ts`)

When `path()` registers a route, it also stores the pattern grouped by the current URL prefix:

```typescript
// In urls.ts path() function
if (ctx.patternsByPrefix) {
  const urlPrefix = getUrlPrefix() || "";
  if (!ctx.patternsByPrefix.has(urlPrefix)) {
    ctx.patternsByPrefix.set(urlPrefix, new Map());
  }
  ctx.patternsByPrefix.get(urlPrefix)!.set(routeName, prefixedPattern);
}
```

### 4. Create separate RouteEntry per prefix (`router.ts`)

```typescript
// Create separate RouteEntry for each URL prefix group
if (patternsByPrefix.size > 0) {
  for (const [prefix, prefixPatterns] of patternsByPrefix.entries()) {
    routesEntries.push({
      // prefix is "" because patterns already include the URL prefix
      prefix: "",
      // staticPrefix is the actual prefix for short-circuit optimization
      staticPrefix: extractStaticPrefix(prefix),
      routes: routesObject,
      // ...
    });
  }
}
```

**Important fix**: We set `prefix: ""` because the patterns stored in `patternsByPrefix` already include the full path (e.g., `/site/:locale/user1/:id`). Setting `prefix` to the include prefix would cause double-prefixing in `findMatch()`.

### 5. Short-circuit check in `findMatch()` (`pattern-matching.ts`)

```typescript
for (const entry of routesEntries) {
  // Short-circuit: skip entry if pathname doesn't start with static prefix
  if (entry.staticPrefix && !pathname.startsWith(entry.staticPrefix)) {
    if (debugEnabled) {
      debugStats.entriesSkipped++;
    }
    continue; // Skip entire entry!
  }

  // ... check routes in this entry
}
```

### 6. Debug utilities for testing

```typescript
let debugEnabled = false;
let debugStats = { entriesChecked: 0, entriesSkipped: 0, routesChecked: 0 };

export function enableMatchDebug(enabled: boolean) {
  debugEnabled = enabled;
}

export function getMatchDebugStats() {
  return { ...debugStats };
}
```

## Debugging Journey

### Issue 1: First optimization attempt made things SLOWER

Initial implementation called `parsePattern()` on every request to extract the static prefix:

```typescript
// BAD - parsing on every request
function canPrefixMatch(pattern: string, pathname: string): boolean {
  const segments = parsePattern(pattern); // Expensive!
  // ...
}
```

**Fix**: Pre-compute `staticPrefix` at registration time, use simple `startsWith()` at match time.

### Issue 2: All routes in ONE entry

Debug stats showed:

```json
{ "entriesChecked": 1, "entriesSkipped": 0, "routesChecked": 14006 }
```

**Root cause**: `include()` was flattening all routes via `processItems()` into the main patterns map, resulting in a single RouteEntry.

**Fix**: Added `patternsByPrefix` Map to group patterns by their include prefix, then create separate RouteEntry objects for each group.

### Issue 3: Double-prefixing bug

After fix #2, routes weren't matching because patterns had double prefixes like `/site/:locale/site/:locale/user1/:id`.

**Root cause**: Patterns in `patternsByPrefix` already include the URL prefix (they're prefixed when `path()` is called inside `include()`). But `findMatch()` was prepending `entry.prefix` again.

**Fix**: Set `prefix: ""` in RouteEntry since patterns already include the prefix. Keep `staticPrefix` for the optimization check.

## Nested Includes Behavior

**Q: Do nested includes also get optimized?**

**A: Yes, but only if their static prefixes differ.**

Each nested `include()` creates a separate `RouteEntry` with its own `staticPrefix`. The `staticPrefix` is extracted from the **combined** URL prefix (parent + child).

### How staticPrefix is computed

```typescript
extractStaticPrefix(pattern) → everything before first : or *

"/api"              → "/api"
"/site/:locale"     → "/site"
"/site/:locale/shop"→ "/site"      // Same as parent!
"/site/shop/:cat"   → "/site/shop" // Different!
```

### Example: No benefit from splitting

```typescript
// Parent include:
include("/site/:locale", localizedPatterns);
// staticPrefix = "/site", 5000 routes

// If you split into nested includes:
include(
  "/site/:locale",
  urls(({ include }) => [
    include("/shop", shopPatterns), // combined = "/site/:locale/shop" → staticPrefix = "/site"
    include("/blog", blogPatterns), // combined = "/site/:locale/blog" → staticPrefix = "/site"
  ]),
);
// ❌ Both have staticPrefix="/site" → NO optimization between shop/blog
// They are separate entries, but can't skip each other
```

### Example: Benefit from restructuring

```typescript
// Restructure to have different static prefixes:
include(
  "/site",
  urls(({ include }) => [
    include("/shop/:category", shopPatterns), // staticPrefix = "/site/shop"
    include("/blog/:category", blogPatterns), // staticPrefix = "/site/blog"
  ]),
);
// ✅ /site/shop/* requests SKIP the /site/blog entry
// ✅ /site/blog/* requests SKIP the /site/shop entry
```

### Rule of thumb

The optimization benefits from **static path segments BEFORE dynamic params**:

| Pattern              | staticPrefix | Optimization         |
| -------------------- | ------------ | -------------------- |
| `/:locale`           | `""`         | ❌ None              |
| `/site/:locale`      | `/site`      | ✅ Skips non-/site   |
| `/site/:locale/shop` | `/site`      | ⚠️ Same as parent    |
| `/site/shop/:cat`    | `/site/shop` | ✅ Skips /site/blog  |
| `/api/v1/:resource`  | `/api/v1`    | ✅ Skips non-/api/v1 |

### When to use nested includes for optimization

1. **DO split** if you can add static segments before params:
   - `/site/shop/:id` and `/site/blog/:id` → different staticPrefix

2. **DON'T expect benefit** from splitting after a param:
   - `/:locale/shop` and `/:locale/blog` → both have empty staticPrefix

3. **Consider route counts**: Only worth splitting if each group has 1000+ routes

## Recommendations

1. **Use static prefixes for large route groups**: `include("/api", ...)` enables optimization; `include("/:locale", ...)` does not (dynamic segment at start)

2. **Order includes by access frequency**: Put most-accessed route groups first to minimize routes checked for cache misses

3. **Consider route group sizes**: Put smaller groups first if they're accessed equally, so fewer routes are checked before skipping

4. **Structure URLs with static segments first**: `/site/shop/:id` optimizes better than `/site/:locale/shop`
