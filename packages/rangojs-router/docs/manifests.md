# Route Manifest System

The route manifest maps route names to URL patterns (e.g., `{ "blog.post": "/blog/:postId" }`).
It powers `ctx.reverse()`, `href()`, and typed `Handler<"name">` without executing handler code at runtime.

## Data Flow

```
Discovery (configureServer / buildStart)
  |
  v
generateManifest() per router
  |
  v
writeRouteTypesFiles() -- writes .named-routes.gen.ts per router
  |
  v
virtual:rsc-router/routes-manifest (load hook)
  |-- imports each .named-routes.gen.js
  |-- calls setCachedManifest(__flat(merged))
  |-- calls setRouterManifest(routerId, __flat(perRouter))
  |-- registers a lazy per-router loader (registerRouterManifestLoader)
  |     -> import("virtual:rsc-router/routes-manifest/<routerId>")
  |        lazily supplies trie + precomputed entries (NOT inlined here)
  |
  v
Runtime: getGlobalRouteMap() / getRouterManifest(id) -> ctx.reverse()
```

## Gen File

Each router gets a `<basename>.named-routes.gen.ts` next to its source file.

```typescript
// Auto-generated by @rangojs/router - do not edit
export const NamedRoutes = {
  "blog.index": "/blog",
  "blog.post": "/blog/:postId",
  // Routes with search schemas use object format:
  "href.filtered": {
    path: "/href/:filterId",
    search: { tag: "string", draft: "boolean?" },
  },
} as const;

// Aliased so the augmentation below does not pay a homomorphic mapped-type
// instantiation per route; `as const` already makes the members readonly.
type NamedRoutesShape = typeof NamedRoutes;

// Module augmentation for typed Handler<"blog.post"> and ctx.reverse("blog.post")
declare global {
  namespace Rango {
    interface GeneratedRouteMap extends NamedRoutesShape {}
  }
}
```

The augmentation targets the global `Rango` namespace (not
`declare module "@rangojs/router"`) and extends `NamedRoutesShape` (an alias of
`typeof NamedRoutes`), so the generated `const` is the single source of truth
for both runtime and types. The alias avoids the homomorphic mapped-type cost
that `Readonly<typeof NamedRoutes>` would incur at the `extends` site.

**Dual purpose:**

- **Runtime data** -- the virtual module imports `NamedRoutes` and calls `setCachedManifest()`; route matching/reverse flattens each entry to its string path.
- **Static types** -- TypeScript uses the `GeneratedRouteMap` augmentation for IDE autocomplete, keeping the per-route search schemas.

`NamedRoutes` stores **path + search** metadata only, sorted by route name.
Auto-generated internal names (`$path_*`, `$prefix_*`) are never written.
Response payload metadata lives in the router builder type
(`typeof router.routeMap`, exposed via `RegisteredRoutes`) and is **not**
emitted into `router.named-routes.gen.ts`. The file has a named export only —
import it as `import { NamedRoutes } from "./router.named-routes.gen.js"`.

### Per-module gen files

Separately from the per-router file, a module that assigns a `urls()` or
`clientUrls()` result can have a sibling `<module>.gen.ts` with only that
module's **local** route names. These are written by the `rango generate`
CLI. The Vite plugin does **not** write them — commit them and re-run
`rango generate` when a module's routes change:

```typescript
// Auto-generated by @rangojs/router - do not edit
export const routes = {
  index: "/",
  post: "/:postId",
} as const;
export type routes = typeof routes;
```

This map has no global augmentation. It is what the client passes to
`useReverse(routes)` to build mount-relative URLs for the module's own routes.

**Two creation paths:**

- `writeCombinedRouteTypes()` -- static parser, runs in `configResolved` (before server starts)
- `writeRouteTypesFiles()` -- runtime discovery output, runs after `discoverRouters()` completes

## Virtual Module

`virtual:rsc-router/routes-manifest` is the bridge between gen files and the runtime.

Generated code (simplified):

```javascript
import { NamedRoutes as _r0 } from "/abs/path/to/router.named-routes.gen.js";
import { setCachedManifest, setRouterManifest, ... } from "@rangojs/router/server";

// Flatten search schema objects to plain string paths
function __flat(r) {
  const o = {};
  for (const [k, v] of Object.entries(r))
    o[k] = typeof v === "string" ? v : v.path;
  return o;
}

clearAllRouterData();
setCachedManifest(__flat(_r0));
setRouterManifest("router_abc123", __flat(_r0));
// Trie + precomputed entries are NOT inlined in this eager module
// (Bundle Hygiene rule #1). A lazy per-router chunk supplies them on demand:
registerRouterManifestLoader("router_abc123", () =>
  import("virtual:rsc-router/routes-manifest/router_abc123"));
```

The RSC entry imports the eager module, and `virtual:rsc-router/loader-manifest`,
only for their side effects, so each `load` hook returns its code with
`moduleSideEffects: "no-treeshake"`. Without it, a build whose
`treeshake.moduleSideEffects` is `false` dropped both, and the server failed at
startup (`src/vite/__tests__/module-side-effects-build.test.ts`).

The eager module carries only the flat route maps (for `ctx.reverse()`); the trie and
precomputed match entries live in the lazy `virtual:rsc-router/routes-manifest/<routerId>`
chunk, populated via `await ensureRouterManifest(routerId)` before any matching.
Keeping that data in exactly one (lazy) chunk is a hard constraint — see CLAUDE.md
"Bundle Hygiene" rule #1; do not inline trie/precomputedEntries data here.
The lazy chunk carries ONLY that derived match data — it does not re-export the
name->path map (the eager module's `setRouterManifest()` is its sole source, and
`ensureRouterManifest()` ignores any `manifest` field on the loaded module).

The `import` of the gen file creates a dependency in Vite's module graph.
When the gen file changes, Vite invalidates the virtual module automatically.
The lazy per-router module keeps a bare side-effect `import` of the gen file for
the same reason: without that edge, a Cloudflare dev program reload re-imports
the cached per-router module and re-installs a stale authoritative trie.

## HMR Flow (Dev Only)

```
Source file change (.ts/.tsx with urls() or createRouter())
  |
  v
Watcher "change" event
  |-- filters: skip .gen.ts, skip "use client", skip non-route files
  |
  v
writeCombinedRouteTypes() -- re-parses static routes from source
  |
  v
supplementGenFilesWithRuntimeRoutes() -- merges factory-only routes
  |-- uses parse cache (avoids redundant I/O per router)
  |-- merges factory route search schemas
  |
  v
Gen file written (only if content changed)
  |
  v
Vite detects file change
  |-- invalidates gen file module in module graph
  |-- invalidates virtual module (imports gen file)
  |
  v
Next request re-evaluates virtual module
  |-- setCachedManifest() called with fresh data
  |-- setRouterManifest() called per router
  |
  v
ctx.reverse() returns updated URLs
```

### Gen File Deletion Recovery

The watcher listens for `unlink` events on `.gen.ts` files:

- If runtime discovery data is available (`perRouterManifests`), calls `writeRouteTypesFiles()`
- Otherwise falls back to `writeCombinedRouteTypes()` (static parser)
- The file is recreated synchronously before the next request

### Factory-Only Routes

Routes from factory functions (e.g., `createDocsPatterns()`) are invisible to the static parser.
`supplementGenFilesWithRuntimeRoutes()` handles this:

1. During discovery, `factoryOnlyPrefixes` is computed -- route name prefixes (e.g., `"docs."`)
   that exist in the runtime manifest but not in the static parser output
2. After `writeCombinedRouteTypes()` writes the static-only gen file, `supplementGenFilesWithRuntimeRoutes()`
   overwrites it with a merged version: static routes + factory-only groups from the runtime manifest
3. Static routes are authoritative (reflecting renames/additions/removals in source);
   factory routes fill the gaps for groups the parser can't resolve

## Multi-Router

Each `createRouter()` gets isolated data:

- `setRouterManifest(routerId, manifest)` -- per-router route map
- `setRouterTrie(routerId, trie)` -- per-router matching trie
- `setRouterPrecomputedEntries(routerId, entries)` -- per-router precomputed leaf entries

`ctx.reverse()` resolves via `getRouterManifest(routerId) ?? getGlobalRouteMap()`.

Search schemas and root-scope flags are per-router the same way: `path()` registers
them under the evaluating router's id (threaded through the evaluation store by
createRouter/generateManifestFull/lazy-include contexts), and lookups pass
`reqCtx._routerId` so same-named routes in different routers keep their own
schema. The name-keyed global tier remains as the fallback for contexts with no
router identity (single-router apps, unit tests).

Per-router virtual modules (`virtual:rsc-router/routes-manifest/<routerId>`) are loaded lazily
via `registerRouterManifestLoader()` / `ensureRouterManifest()` on first request — in BUILD
only. `ensureRouterManifest()` marks a loader-supplied trie authoritative (misses are hard
404s), which is only valid for a trie serialized from complete build-time discovery. Dev
never registers loaders: the handler rebuilds the trie from live `router.urlpatterns`
(`buildRouterTrieFromUrlpatterns`, non-authoritative), so a Cloudflare program reload can
never serve a removed route from a stale-but-authoritative discovery trie.

Router roots must be sibling app roots. Nested router roots are not supported:
if a router source file lives under another router's directory, Vite runtime
discovery and `rango generate` fail with an explicit error. This keeps static
route-type generation scoped to the nearest router root and avoids deep
redundant filesystem scans in large projects.

## Static vs Runtime Generation Boundary

The CLI (`rango generate <file|dir> [--runtime|--static] [--config <path>]`)
has three modes for producing `.named-routes.gen.ts`:

| Mode             | Flag        | Discovery                                                        | Coverage                                                |
| ---------------- | ----------- | ---------------------------------------------------------------- | ------------------------------------------------------- |
| Static (default) | (none)      | AST-only, no Vite server                                         | Named routes visible to the static parser; fails fast   |
| Static, partial  | `--static`  | AST-only, no Vite server                                         | Same, but accepts partial output with warnings          |
| Runtime          | `--runtime` | Spins up a temp Vite server, imports entry via RSC module runner | 100% of registered routes (`--config` picks the config) |

**Design rule:** when the static parser encounters route tree structures it
cannot reconstruct (factory function calls, dynamic expressions, conditional
registrations), it must **fail fast with a clear diagnostic** pointing the
user to `--runtime`. It must never silently emit incomplete or wrong output
in default mode.

Concretely:

- `detectUnresolvableIncludes()` scans router files for `include()` calls
  whose second argument is a function call or expression the parser cannot
  resolve. These are classified as `"factory-call"` or `"unresolvable"`.
- In default mode, any unresolvable include causes a hard error with the
  list of unresolvable prefixes and the suggestion to use `--runtime`.
- In `--static` mode, partial output is accepted with a warning.
- In `--runtime` mode, the Vite server evaluates the actual module graph,
  so factory functions execute and all routes are discovered.

This is intentional: "hard runtime augmentation parity" is not a goal of
the static parser. The static parser is a fast, dependency-free path for
the common case. When the route tree is too dynamic for static analysis,
the correct answer is `--runtime`, not a best-effort guess.

## Configuration

There is no manifest-specific option: the `rango()` Vite plugin runs discovery
and writes the per-router `*.named-routes.gen.ts` on its own, whatever the
preset. `rango generate` is needed for per-module `.gen.ts` files and outside
a Vite run (for example in CI before `tsc`).

```typescript
rango({
  preset: "cloudflare",
});
```

## Build vs Dev

| Aspect             | Dev                                     | Build                                          |
| ------------------ | --------------------------------------- | ---------------------------------------------- |
| Discovery          | `configureServer` hook, live RSC runner | `buildStart` hook, temp Vite server            |
| Gen file updates   | File watcher + supplement               | Single write after discovery                   |
| Virtual module     | Re-evaluated on each request after HMR  | Bundled by Rolldown (gen file inlined)         |
| Manifest readiness | `manifestReadyPromise` gate             | Synchronous (discovery completes before build) |

Both modes produce the same virtual module output. The `import` from gen file works in both:
Vite resolves it in dev, Rolldown (Vite 8) bundles it in build.

### Dev-boot module reload races (why discovery checks its realm)

Boot discovery reads `RouterRegistry` and installs clientUrls projections on one
`@rangojs/router/server` instance, and that has to be the instance the RSC runner serves
once the entry is imported. Two bugs taught us this:

- **Dependency re-optimization (#637).** On a cold dev boot that also triggers a Vite
  dependency re-optimization (first boot after a lockfile change, or `vite dev --force`),
  a module imported through the RSC runner _before_ the entry could resolve to the
  **pre-optimize** copy of the runner's module graph, while the entry import, which awaits
  the in-flight re-optimization, resolves to the **post-optimize** copy. `createRouter()`
  populated `RouterRegistry` on the fresh copy, the stale copy read an empty `Map`, and
  discovery threw a spurious `No routers found in registry after importing <entry>`.
- **Runner full reload mid-pass.** A full reload clears the runner's
  evaluated-module cache. One that lands while the entry is importing splits the realm:
  the router module, already bound to the old copy, registers there, while `urls.tsx`
  re-evaluates against a fresh copy whose clientUrls projection `Map` is empty. Discovery
  had installed the projections on the old copy, so `include()` of a clientUrls module
  threw `include() could not resolve the server projection`, and every request returned a
  500 until a restart.

`discoverRouters()` imports `@rangojs/router/server` before the entry, because the pre-entry
clientUrls refresh needs it (`refreshRecordedClientUrlProjections`), and treats that
instance as the pass's realm baseline. After the entry import, after host-router
resolution, before it commits, and on any error, it re-imports `@rangojs/router/server`;
if the runner now serves a different instance, it redoes the pass (`runnerReloadedSince`,
at most `MAX_DISCOVERY_PASSES` = 3). The redo evaluates the entry in one realm, since the
reload dropped the half-evaluated graph. The Node dev path arms `manifestReadyPromise`
**after** `discoverRouters()` on the instance it returns; the virtual manifest module's own
`s.discoveryDone` gate already blocks early requests during discovery. Never read the
registry or install projections on an instance the pass has not verified; that re-opens
both races.

Backstops for a cold discovery that still fails: the per-request self-heal in `handler.ts`
builds the trie from the router's live `urlpatterns` when the manifest is missing, and
`describeDiscoveryFailure()` (discovery-errors.ts) downgrades the terminal message to an
informational warning when the dep optimizer's `browserHash` changed across the attempt,
reserving the loud, actionable error for a genuinely empty registry. A failed cold
discovery commits nothing, so the routes-manifest module's no-manifest branch still replays
`state.clientUrlProjectionMap` (the projections the failed pass computed), and the failure
sets `lastDiscoveryError` (`recordDiscoveryFailure`): `canRefreshRuntimeDiscovery()`
(discovery/state.ts) then lets the route-file watcher re-run discovery, the recovery mode a
failed HMR rediscovery already had. Before, the watcher required a committed manifest, so
only a restart recovered.

Cloudflare needed the same recovery a second time. Its cold discovery runs on the temp Node
server, and a failure there (the temp runner's entry import throwing, or `discoverRouters`
giving up) recorded nothing, while `refreshRuntimeDiscovery` returned early with no
committed manifest. That left the same 500s as on Node. The worker builds its dev trie from
the live route tree (`buildRouterTrieFromUrlpatterns`), which evaluates every `include()`,
and it gets its clientUrls projections only from the routes-manifest module. A cold failure
before the projections were computed made that build throw
`include() could not resolve the server projection` on every request, and no save cleared
it. Both failures now record `lastDiscoveryError`. The recovering save re-runs discovery on
the temp runner (`getOrCreateTempServer` creates a fresh one when the failed start closed
it), and the worker reload that follows (`forceCloudflareWorkerReload`) invalidates the
worker's whole module graph, routes-manifest module included, so the Node path's explicit
invalidation is not needed there.

That recovery has one cost we accepted: recovery mode re-runs discovery on every in-scan save
until a pass succeeds. On Cloudflare, an app whose temp runner can never import the entry
(an entry Node cannot evaluate) creates and closes a temp Vite server on each save while
`lastDiscoveryError` stays set, and prints two warnings per save ("Failed to create temp
runner", then "Runtime re-discovery failed"). It is one attempt per save, never a loop, and
each server is closed. Such an app had no working discovery before this change either.

Pinned by `src/vite/__tests__/dev-discovery-recovery.test.ts`, which drives the plugin's
`configureServer` against fake Node and Cloudflare dev servers, and by
`tests/cloudflare-basic/e2e/hmr-cold-discovery-recovery.test.ts` (local only, like the other
route-edit e2e), which boots a real Cloudflare dev server on a discovery-only failure.

### A reload no file of the app asked for (why the watcher skips some directories)

The realm check above protects discovery. It cannot protect a request that is already
running in the Cloudflare worker when a re-discovery reloads it: the reload clears the
runner's evaluated-module cache, and every dynamic import the request makes afterwards
(`buildRouterTrieFromUrlpatterns`'s `import("../build/generate-manifest.js")`, an async
`include()`, a lazy loader) evaluates a second copy of the router with empty registries.
That request then fails with `include() could not resolve the server projection`,
`Projected loader … was not found in the server loader registry`, or
`getRequestContext() called outside of a request context`, because each registry and the
request-context `AsyncLocalStorage` live in module scope.

A real route edit pays that once, and the next request is fine. What made it a bug was a
reload nothing in the app asked for: the cache-version e2e copied a whole app (its own
`router.tsx` and `urls.tsx`) into `.cache-version-work/` inside the cloudflare-basic root
whenever Playwright collected tests. The route-file watcher matched those files, re-ran
discovery, and the reload landed during a cold dev server's first request, so a single
clientUrls test failed 9 of 10 cold runs.

So the watcher ignores a file in a directory every discovery scan skips, unless the RSC
module graph has loaded it (`isFileOutsideApp` in `router-discovery.ts`). "Every scan" is
literal: `isUniversallySkippedScanDir` in `scan-filter.ts` is the one predicate
`findTsFiles`, `findRouterFiles` and `findHostRouterFiles` all build on, so the watcher
and the scans cannot drift apart. It names dot-directories, `node_modules`, `dist` and
`coverage`. `build`, `__tests__` and `__mocks__` are not in the set: each is skipped by
only one of the scans (`findTsFiles` skips `build` through `isSkippedSourceScanDir`, the
rule the build loader pre-scan in `expose-internal-ids.ts` shares; the router scans skip
the other two), and on Cloudflare the worker's module graph is empty until the first request, so an edit
to a router or `urls()` module under one of them must still re-run discovery.

A nested checkout under `.claude/worktrees/` or a tool's working copy can no longer reload
your dev worker; a route module that does live in a dot-directory re-runs discovery once the
app imports it. Pinned by `tests/cloudflare-basic/e2e/dev-cold-start.test.ts`, the
`isFileOutsideApp` tests in `src/vite/__tests__/route-watcher-scope.test.ts`, and the
`isInSkippedScanDir` table in `src/build/__tests__/generate-route-types.test.ts`.

### A request the reload split (why a dropped router hands its requests off)

Skipping directories removed one reload nobody asked for. A cold dev start has another
that no rango setting can avoid: Vite's dep optimizer finds an RSC dependency its scan
missed, re-optimizes, and when the optimized files changed it ends with
`moduleGraph.invalidateAll()` and `full-reload`, logged as
`(rsc) optimized dependencies changed. reloading` (#1186). On a cold `node_modules/.vite` it
lands during the first request, while that request is still evaluating the entry.

That request's module chain then splits. What it imported before the clear stays in the old
copy: `@rangojs/router`, the include helper, everything `urls.tsx` imported first. What it
imports after the clear is a fresh copy: the clientUrls() groups imported later in
`urls.tsx`, their `?rango-revalidate` modules with the `@rangojs/router/server` those import,
the handler `router.fetch` lazy-imports on its first call, and the deps under their new
`?v=` hash. The groups registered their hoisted `revalidate()` predicates in the fresh
copy's registry, while the old `include()` materialized through the old one. The old copy
never saw the key, so the page answered 500 with
`clientUrls() revalidate() … has no server registration`. Every request after it ran on the
fresh copy and worked.

Moving the registry to `globalThis` only moves the 500 to the next error. We measured each
step on cloudflare-basic, with the reload forced at the first request:

1. With the registry moved, the request failed with
   `getRequestContext() called outside of a request context`: the old copy's middleware
   read the old `AsyncLocalStorage` while the fresh copy's handler ran in the new one.
2. With that store moved too, it failed with
   `Projected loader … was not found in the server loader registry`.
3. With the loader store moved as well, `/` answered 200 but rendered the catch-all page:
   the old matcher read a trie that the fresh copy had built.

No set of stores can make that request consistent. After a real re-optimization, Vite's
optimizer keeps the old `browserHash` only when no reload is needed (`commitProcessing` in
its `optimizer.ts`). So the modules transformed after the reload import React under a new
`?v=` hash, and the two halves of the request run two copies of React.

So the request moves instead (`src/router/dev-reload-handoff.ts`). Every copy of that module
listens for `vite:beforeFullReload` through `import.meta.hot`; once the event fires, its copy
counts as dropped. `router.fetch` of a router a dropped copy created imports the router's
`$$sourceFile` through the runner, then reads the fresh `RouterRegistry`, and calls that
router's `fetch`, so the request runs once, on one module set. If the fresh module throws,
that error becomes the request's error. This is the request-side twin of the discovery pass
that `runnerReloadedSince` redoes. Both branches sit behind
`process.env.NODE_ENV !== "production"`, which a build folds, so a worker bundle carries none
of it.

The import alone does not wait for the reload. While the runner's re-import of the entry is
still evaluating the router's module, the runner hands this importer the unfinished module:
the router's file is in the import call stack of the dropped copy (`cachedRequest` in Vite's
`module-runner.js`). So when the fresh registry has no router under the id yet, the hand-off
polls it every 20 ms for up to 10 s (`DEV_RECREATED_ROUTER_WAIT_MS`; cloudflare-basic's
entry took about 5 s to re-evaluate after `invalidateAll`). A Node runner reaches that case.
On Cloudflare we measured that the runner worker dispatches the split request's `fetch` only
once the re-import has finished, 1 ms after the fresh entry finished evaluating, even with
that re-import held for 8 s. So there the router is already registered.

Checking at the top of `fetch` is not enough on its own. In an app whose worker entry does work
of its own before `router.fetch`, the first request entered `fetch` while the copy was still
current, and the reload landed 1.24 s later, during route discovery. Discovery then imported an
async `include()`'s group after the clear, so the same 500 came back on 0.26.3 (#1186, reopened).
A check at the entry cannot see a reload that comes after it. So `serveAcrossRunnerReload` also
looks once the handler settles: if the reload dropped this copy while a GET or HEAD request ran,
it throws away the outcome, whether that was an error or a response (it cancels the body), and
runs the request again on the re-created router. It does not stop at a failure, because a split
request can also answer 200 with the wrong route (step 3 above). An error that escaped the
discarded run is dropped without a print, while what that run already logged or reported to
`onError` before it settled (a loader error, say) stays. A real failure fails the re-run too, so
you still see it.

It does not catch everything. These cases still run on the split module set:

- a reload that lands after the handler returned its response, while the body streams;
- a request with any other method that the reload lands inside: a re-run would repeat its side
  effects (a server action, say), and the first run read its body;
- a re-import that has not registered the router when the wait runs out;
- a router built in a factory, since importing its `$$sourceFile` does not create it, so the
  wait runs out;
- `createHostRouter()` itself (its patterns and middleware); a `router.fetch` it dispatches
  to still hands off.

The discovery-probe check stays ahead of the hand-off, so a dropped router still answers
probes with its own epoch without rendering. Pinned by
`src/router/__tests__/dev-reload-handoff.test.ts`, by
`src/router/__tests__/dev-reload-handoff-runner.test.ts` on a real Vite module runner whose
re-import is still loading the router, and by `tests/cloudflare-basic/e2e/dev-rsc-reload.test.ts`.
That e2e sends the optimizer's reload where a cold server's first request loads a probe module,
and holds the re-import for 2 s (`RANGO_E2E_RSC_RELOAD_PROBE`). With `entry`, the probe is
`src/rsc-reload-probe.ts` and loads while the entry evaluates. With `discovery`, it is
`src/rsc-reload-probe-discovery.ts`, which the async include of `/__client-urls-lazy` loads during
route discovery, before a group nothing else imports (`src/client-urls/lazy.tsx`).

## Runtime Storage

Three tiers in `route-map-builder.ts`:

| Storage                | API                                           | Purpose                                                             |
| ---------------------- | --------------------------------------------- | ------------------------------------------------------------------- |
| `cachedManifest`       | `setCachedManifest()` / `getGlobalRouteMap()` | Global merged manifest from all routers                             |
| `perRouterManifestMap` | `setRouterManifest()` / `getRouterManifest()` | Per-router isolated manifests                                       |
| `globalRouteMap`       | `registerRouteMap()`                          | Runtime-accumulated fallback (used before virtual module evaluates) |

`getGlobalRouteMap()` returns `cachedManifest` if available, otherwise `globalRouteMap`.

**Internal only:** The storage functions in `route-map-builder.ts` (`getGlobalRouteMap`,
`getRouterManifest`, `clearCachedManifest`, etc.) are exported from `@rangojs/router/server`
but marked `@internal`. They are consumed by the virtual module and internal Vite plugin
code only. User-land code should use `ctx.reverse()` or `href()` to resolve route names —
never access the manifest storage directly.
